# 设计：确定性引擎的「无故障出口」

> 状态：**已登记，未实现**。实现需同时改 `router.py` 与 `orchestrator.py`（见改动点）。

## 为什么要有它（实测缺陷，不是设想）

`tools/false_positive_probe.py` 给 8 个"系统其实没坏"的输入，每例采样 3 次：

| 输入 | 结果 |
|---|---|
| 系统当前状态正常，没有异常 | 3 次里 2 次断言了故障 |
| 复制中断**已恢复**、io/sql 均为 ON | **3/3 断言**（数据） |
| 30 分钟前一次 HTTP 500、之后无复现 | **3/3 断言**（资源） |
| t_txn 行数增长与往常一致、副本延迟为 0 | **3/3 断言**（数据） |
| 今天天气怎么样？ | **3/3 断言**（配置/数据/?） |

汇总：**假阳性 22/24 = 91.7%**；**确定性路径 15/15 全部断言**，agentic 路径 7/9。
即：这套系统目前只会"找到根因"，**没有"说没问题"的能力**。

在只测正例的评测台上（只问"能不能找到根因"），这个缺陷**永远不会暴露** ——
这正是把阴性用例纳入评测的理由。

## 契约

被判为无故障时，响应必须满足：

1. `root_cause.category` 为「无故障」（与既有「非真实故障」表述一致）
2. **不得**给出 `rc:*` 根因术语，也不得把任何实体指为故障点
3. `description` 说明**为什么**判为无故障，并引用输入中的证据（如 io/sql 均为 ON）
4. **零步骤、零 token** —— 确定性路径，不调用 LLM
5. `mode` 为 `no_fault`（新增值，便于前端与评测区分"拒答"与"诊断"）

## 触发条件

- 明确陈述"正常 / 无异常 / 无告警"
- 明确陈述"已恢复 / 已回滚"并给出恢复证据
- 明确陈述"单次 / 瞬时且未复现"
- 与系统无关的输入（闲聊、外部组件）
- 只陈述"与往常一致 / 无变化"

**反向约束（防止退化成"什么都不报"）**：21 个真实故障用例必须**仍然**给出根因。
因此验收必须**双向**：阴性 8 例全判无故障 **且** 阳性用例不退化。

## 独立缺陷：路由不确定性

同一输入在不同运行间**有时走确定性、有时走 agentic**（探针输出出现 `路径=agentic,deterministic`）。
这不是"答案在变"，而是**路由本身在变**。后果：`e2e 16/18`、`A/B 17→18` 等对外数字
都存在**运行间方差**，而它们一直被当作确定量报告。需单独复测并标注误差范围。

## 验收顺序（严格）

1. 实现 `no_fault` 出口 → 跑 `false_positive_probe`（阴性）必须全绿
2. **再**跑 `fault_injector verify` + `cluster_rca_verify`（阳性）必须不退化
   —— 否则是"修好一边、弄坏另一边"，比不修更糟
3. 复测路由方差，为 e2e/A/B 数字标注误差范围
