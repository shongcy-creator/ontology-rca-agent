## 1. 集群拓扑

```
                        外部客户端
                            │  :8080
                 ┌──────────▼───────────┐
                 │  cc-app-gateway      │  Nginx · least_conn · Docker DNS 发现
                 │  (负载均衡 / 唯一入口) │  /gateway/health /gateway/status
                 └──────────┬───────────┘
              ┌─────────────┼─────────────┐
              ▼             ▼             ▼
      payment-app-1  payment-app-2  payment-app-3    每副本：cpus=0.5 mem=256m
      (cc-payment-app-N, 无固定 container_name → 可水平扩缩)   NET_ADMIN(tc)
              │             │             │
              │  写 → 主库   │  读 → 副本（轮询 mysql-replica-1/2）
              ▼             ▼             ▼
      ┌───────────────────────────────────────────────┐
      │            数据库层集群（GTID 异步复制）          │
      │  cc-mysql-core (PRIMARY, server_id=1, :3306)   │
      │        │ binlog/GTID                          │
      │        ├──────────► cc-mysql-replica-1 (11)    │ mem=768m, read_only+super_read_only
      │        └──────────► cc-mysql-replica-2 (12)    │
      └───────────────────────────────────────────────┘

      监控：Prometheus(:9090) ── dns_sd 发现全部 app 副本
                              ── 3 × mysqld-exporter（primary / replica-1 / replica-2）
                              ── blackbox-exporter 探活（网关 + 每个副本直连）
           Grafana(:3000)     Agent UI(:3001)      Agent API(:8088)
```

设计要点（都是"为了让 RCA 有东西可查"而做的）：

1. **副本数不足 vs 整层不可用要能区分** → 用 `count(up{job="payment-app"} == 1)` 而不是单个 `up`。
2. **副本自报健康 ≠ 用户能访问** → 引入 blackbox-exporter 做外部探活（`probe_success`），
   否则"网关挂掉但副本全健康"根本无法发现。
3. **容器资源指标必须是 cgroup 级** → 应用 `/metrics` 直接读 `/sys/fs/cgroup`，
   暴露 `cc_container_memory_working_set_bytes / _limit_bytes`
   与 `cc_container_cpu_nr_throttled_total`。
   （`process.memoryUsage()` 只能看到 Node 进程，看不到 `docker exec` 起的压力进程。）
4. **读写分离让副本故障有业务含义** → 应用读路径轮询只读副本，
   副本挂了/延迟了会真实反映为"读到的数据陈旧 / 读接口 503"。

## 3. 应用层集群化

### 3.1 改动清单

| 文件 | 改动 |
|---|---|
| `rca-agent/docker-compose.yml` | `payment-app` 去掉 `container_name` + `deploy.replicas: 3`；新增 `app-gateway`；加 `cpus/mem_limit/cap_add: NET_ADMIN`；新增 blackbox-exporter |
| `rca-agent/gateway/nginx.conf` | upstream `payment-app:8080` + `resolve`（Docker DNS 动态发现）；`least_conn`；`proxy_next_upstream` 快速摘除坏副本 |
| `demo/app/server.js` | 实例身份 `app_instance`、读写分离、连接池 `waiting`、cgroup 内存/CPU 节流指标、`/instance` `/txn/recent` |
| `demo/app/Dockerfile` | `apk add iproute2 stress-ng procps curl bash`（故障注入所需的容器内工具） |

### 3.2 实例身份与标签约定

* 副本身份 = `APP_INSTANCE` 环境变量，未设置时回退到容器 `HOSTNAME`（Docker 注入的容器 ID 前 12 位）。
* 该身份以 **`app_instance`** 标签出现在所有指标上，而不是 `instance`。
  原因：Prometheus 的 target 标签也叫 `instance`，同名会被改写成 `exported_instance`，
  对模型/人都不友好。target 侧 `instance` 被 relabel 成纯 IP（可读），
  业务侧 `app_instance` 是容器 ID（可与 `docker ps` 的 ID 对齐）。

### 3.3 修掉的一个真实缺陷（否则故障信号会被污染）

原 `POST /txn` 的异常路径**不归还连接**：

```js
const conn = await pool.getConnection();
await conn.query('INSERT ...');   // 抛错
// ← catch 里没有 conn.release()
```

后果：主库被置为只读时，"写失败 → 连接泄漏 → 连接池（limit=10）耗尽 →
后续请求全部挂起"，实测 20s/16 并发下 **32/41 请求超时**、只有 9 个返回 5xx。
5xx 是这条故障链的关键证据，却被超时掩盖。

修复（`finally` 中无条件 `release`）后同一故障下 **5698/5698 全部返回 503**、
无超时、连接池指标可信。这是一个"为了让 RCA 证据链干净而必须修的业务 bug"。

### 3.4 新增可观测指标

| 指标 | 含义 | 用途 |
|---|---|---|
| `cc_app_instance_info{app_instance,version}` | 副本身份（恒为 1） | 标识副本，配合 `docker ps` 定位容器 |
| `cc_mysql_pool_waiting` | 等待连接的请求数（排队） | 连接池耗尽的最直接证据（比 active 更早、更准） |
| `cc_mysql_up` / `cc_mysql_replica_up{replica}` | 主库/副本可达性 | 读写分离链路健康 |
| `cc_container_memory_working_set_bytes` | cgroup 内存用量 | OOM 前兆 |
| `cc_container_memory_limit_bytes` | cgroup 内存上限 | 计算使用率分母 |
| `cc_container_cpu_nr_throttled_total` | 被节流的 CPU 周期数 | CPU 配额不足（`cpus=0.5`） |
| `cc_container_cpu_throttled_seconds_total` | 被节流的累计时间 | 同上，量化严重度 |

## 4. 数据库层集群化

### 4.1 拓扑与配置

| 节点 | 容器名 | server_id | read_only | mem_limit | 角色 |
|---|---|---|---|---|---|
| 主库 | `cc-mysql-core` | 1 | 0 | 1g | 全部写入，产生 binlog/GTID |
| 副本 1 | `cc-mysql-replica-1` | 11 | 1（引导后 `super_read_only=ON`） | 768m | 只读副本，回放主库 GTID |
| 副本 2 | `cc-mysql-replica-2` | 12 | 1（同上） | 768m | 只读副本 |

三节点均开启：`gtid-mode=ON` `enforce-gtid-consistency=ON` `binlog-format=ROW`
`log-replica-updates=ON`，复制使用 `SOURCE_AUTO_POSITION=1`。

### 4.2 `tools/cluster_bootstrap.py`（幂等引导）

1. 等 3 个节点健康（`mysqladmin ping`）
2. 每个节点上创建/刷新账号（**先临时关闭 `super_read_only`**，否则 `CREATE USER` 报 1290）：
   * `rca_readonly`（PROCESS + REPLICATION CLIENT + SELECT creditcard/performance_schema）→ exporter 与 Agent 取证共用
   * `appuser`（追加 `SELECT ON creditcard.*` —— 缺这一条会出现"读写分离后读路径 503"）
3. 主库创建复制账号 `repl`（`mysql_native_password` + `REPLICATION SLAVE`）
4. 副本首次引导：`RESET BINARY LOGS AND GTIDS`（回退 `RESET MASTER`）→
   `mysqldump --single-transaction --set-gtid-purged=ON` → 导入 →
   `CHANGE REPLICATION SOURCE TO ... SOURCE_AUTO_POSITION=1, GET_SOURCE_PUBLIC_KEY=1` → `START REPLICA`
5. 校验 IO/SQL 线程 Running + `Seconds_Behind_Source=0`
6. 收紧副本为 `super_read_only=ON`，写快照到 `.chaos/cluster_state.json`

**只复制业务库 `creditcard`**（账号在各节点独立创建），避免把主库账号体系与时序问题带进副本。

### 4.3 已知坑（脚本里都已处理）

| 现象 | 原因 | 处理 |
|---|---|---|
| `ERROR 1290 ... --super-read-only` | 上一次引导后副本已收紧只读，再建账号被拒 | 建账号/改复制前先 `SET GLOBAL super_read_only=OFF` |
| `INSERT ... WITH RECURSIVE` 静默插 0 行 | `cte_max_recursion_depth` 默认 1000 | 插入前 `SET SESSION cte_max_recursion_depth=<块大小+10>` |
| `RESET BINARY LOGS AND GTIDS` 不存在 | 版本差异 | 回退 `RESET MASTER` |
| 读路径 503，报权限错误 | 副本上 `appuser` 缺 `SELECT ON creditcard.*` | 引导脚本统一补授权 |
| exporter 起不来（`no user specified`） | mysqld-exporter v0.16 已移除 `DATA_SOURCE_NAME` | 改用 `--mysqld.address/--mysqld.username` + `MYSQLD_EXPORTER_PASSWORD` |

## 6. 故障注入程序（`tools/fault_injector.py`）

### 6.1 架构

```
tools/chaos/core.py       基础设施：docker/SQL/Prometheus 访问 · Fault 模型 · 状态文件 · 注入引擎
tools/chaos/catalog.py    故障目录：21 个场景的 inject / recover 实现
tools/fault_injector.py   CLI：doctor / list / status / seed / inject / recover / run / verify
.chaos/fault_state.json   注入状态（回滚所需全部信息）→ 进程被杀也能 recover --all
```

三条设计原则：

1. **可回滚**：每次注入把 `fault_id + targets + params + recover_hint` 落盘；
   回滚是**数据驱动**的（不依赖内存闭包），`recover --all` 永远安全。
2. **可验证**：每个场景声明 PromQL `signals`，注入后引擎等待至少一条变为真，
   避免"注入了但没有任何可观测证据"的假成功；同时声明 `recovered_signals`
   做回滚校验（`expect=falsy`）。
3. **诊断/注入分离**：故障注入只操作模拟环境；Agent 侧工具链依旧全部只读。

### 6.2 信号表达式书写约定（踩过的坑）

PromQL 里 `bool` 是**比较运算符的修饰符**，不是函数，`bool(expr)` 是语法错误。
而判定规则若统一为"样本值 > 0 即成立"，那么 `up{job="x"} == 0` 这种过滤式表达式
在条件成立时返回的样本值恰好是 **0**，会被误判为"不成立"。

约定：**信号表达式在条件成立时必须返回数值 > 0 的序列**。

```promql
✔ count(up{job="payment-app"} == 1) < 3      # 成立时返回 1
✔ max(a / b) > 0.8                            # 成立时返回 1
✔ rate(x[2m]) > 0                             # 成立时返回 1
✘ up{job="x"} == 0                            # 过滤式：成立时返回 0 → 误判
   应写成  count(up{job="x"} == 0) > 0
```

另外：计数器类信号的**恢复校验必须用短窗口**。`rate(nr_throttled_total[3m])`
在压力停止后仍会 > 0 长达 3 分钟，用 3m 窗口做 `recovered_signals` 会误报"未恢复"。

### 6.3 场景目录（21 个）

**应用层（9）**

| `app_kill_replica` | `docker kill` 一个副本 | 资源 | 健康副本数 < 3 |

### 6.5 "注入了但什么也没发生"——三个真实反例（已修正）
| 场景 | 初版问题 | 修正 |
|---|---|---|
| `db_row_lock_hold` | 只锁单行（`WHERE txn_id=1`），INSERT 新行不冲突 → `innodb_row_lock_current_waits` 恒为 0 | 改**全表** `FOR UPDATE`（REPEATABLE READ 下加 next-key 锁覆盖 supremum gap），并起后台受害者写会话，使阻塞在注入阶段即可观测 |
| `db_replica_lag` | `SOURCE_DELAY` 生效但没有新事务可回放 → `Seconds_Behind_Master` 恒为 0 | 注入时同时起后台写流（`chaos-lag-writer`），保证"延迟"可观测 |
| `app_cpu_stress` | 用 `rate(cc_container_cpu_seconds[3m])` 判断——但那是 **Node 进程** 的 CPU，`stress-ng` 是另一个进程，指标不动 | 改用 cgroup 节流指标 `cc_container_cpu_nr_throttled_total`，并在应用内新增 cgroup 采集 |

#### 架构：复用同一份引擎，不重写

```
浏览器 (localhost:3001)
   │  /api/chaos/*           ← nginx 反代
   ▼
rca-agent-backend (FastAPI :8088)
   │  backend/routers/chaos.py      接口层（闸门/任务/信号）
   │  backend/services/chaos.py     任务引擎（单飞锁 + 日志缓冲 + 轮询）
   │  from tools.chaos import ...   ← /app/tools 只读挂载（与宿主机 CLI 同一份代码）
   │  /app/.chaos                    ← 读写挂载（与 CLI 共享 fault_state.json）
   ▼
docker CLI + /var/run/docker.sock（容器内已有，无需新增权限）
   ▼
payment-app ×3 / mysql ×3 / cc-app-gateway
```

compose 只需给后端加两行挂载 + 几个环境变量（`../tools:ro`、`../.chaos`、
`CHAOS_PROM_URL/CHAOS_APP_LB/CHAOS_RCA_API`——注入器原本硬编码 `localhost`，
容器内必须换成 compose 服务名）。

#### 三个必须处理的工程问题

| 问题 | 处理 |
|---|---|
| 注入是**长阻塞**操作（等 PromQL 信号最长 75s；`db_replica_lag` 回滚要等复制回放最长 150s） | 所有写操作变成**后台任务**：接口立刻返回 `job_id`，前端 1s 轮询 `/jobs/{id}?since=N` 增量取日志 |
| 两个注入同时跑会**互相污染信号**，回滚互相踩 | 全局**单飞锁**：同一时刻只允许一个任务；面板直接提示"已有任务在运行" |
| 状态文件必须与 CLI 共享（它是进程被杀后回滚的唯一依据） | `.chaos/` 读写挂载进容器；面板显示的"激活故障" = `fault_injector.py status` 的结果 |

#### 人工操作的安全护栏

1. **二次确认**：`critical`/`high` 场景（网关停机、杀副本、OOMKill、主库只读…）
   必须显式确认才允许注入，后端返回 409 + `need_confirm`，前端弹模态展示影响面。
2. **不允许叠加**：已有激活故障时拒绝新注入（否则信号互相污染、RCA 结论不可信），
   必须"先回滚再注入"。
3. **参数白名单**：只接受场景声明的参数，且做类型收敛（避免手滑传任意值）。
4. **紧急清理**：`🚨 紧急清理` 走的是"不依赖状态文件"的兜底路径
   （扫容器内压测进程 / 注入循环 / 残留会话 / 被改过的全局变量 / 只读配置 / cgroup 内存上限），
   即使后端进程被杀也能复原环境。
5. **可选令牌**：`CHAOS_API_TOKEN` 非空时，所有写操作必须带 `X-Chaos-Token`。
6. **总开关**：`CHAOS_UI_ENABLED=0` 可整体停用注入接口（只读接口不受影响）。
7. **目标白名单**：前端会把**预览到的目标容器**回传给 `/inject`（做到"预览即实际目标"，
   `roundrobin` 场景尤其需要），因此后端必须校验 ——
   只有"运行中的应用副本 + 网关 + 三个 MySQL 节点"在允许列表内，
   传别的容器名一律 400。否则等于把"向任意容器投递命令"的能力开放给 HTTP 调用方。

> ⚠️ **安全边界**：控制台能通过 docker socket 在集群里制造故障，
> 权限等价于"能操作这些容器"。默认无鉴权是为了本地演示方便；
> 对外暴露前请务必设置 `CHAOS_API_TOKEN`，并把 8088/3001 限制在可信网络。

#### 与"智能体不知道答案"的关系

控制台是**出题方**的界面，所以它会显示 `expected_root_cause`（标准答案），
但页面明确标注「仅供人工对照，**不会发送给智能体**」；
「到诊断台 →」交接的是**中性文案**
（`neutralPrompt()`：症状 + 告警来源 + 层 + 场景标题，不含根因描述），
因此 `§8.2 不向智能体泄露答案` 的前提依然成立。

#### ⏹ 停止并回滚（误点演练的紧急出口）

「批量演练」是**一次 20–40 分钟、依次注入全部 21 个场景**的破坏性操作，
误点的代价很高 —— 因此它有两道保护：

1. **二次确认**：点击后弹模态，明确写出场景数、预计时长、"随时可停止"；
2. **运行中必有停止按钮**：只要有任务在跑，顶部与日志面板都会出现
   红色脉冲的 **「⏹ 停止并回滚」**（替换掉「批量演练」按钮的位置）。

![停止并回滚](images/故障注入_停止并回滚.png)

> 上图为真实截图：本页**从未提交过**这次演练（它是脚本启动的），
> 面板仍通过状态轮询**接管**了它并显示了停止按钮 ——
> 这一点很关键，否则"刷新页面后看不到停止按钮"就等于停不下来。

**取消是"协作式"的，不是强杀线程**。为什么：

> 一次注入是**有副作用的多步操作**（改 cgroup 上限、拉起后台循环、改 MySQL 全局变量、
> 置主库只读…）。在任意一行强杀线程会留下**半注入状态**，
> 而回滚恰恰依赖"这些步骤是否被完整记录" —— 半注入比重启后端危险得多。
> 所以实现为：置位取消标志 → 任务在**下一个取消点**停止 → **必定执行回滚 + 收尾清理**。

取消点覆盖每一处长阻塞（否则用户会以为点了没反应）：

| 阻塞点 | 原最长阻塞 | 取消后 |
|---|---|---|
| 注入阶段的等信号（`inject` 内） | 75s | ≤5s |
| 压测窗口内等信号 | 75s | ≤5s |
| 保持期 `hold_s` | 20–90s | ≤0.5s（可中断 sleep） |
| 停后台压测的宽限期 | 15s | 3s |
| 场景间隔冷却 | 8s | ≤0.5s |
| 恢复校验宽限期 | 90–150s | 30s |
| 场景边界 | 不适用 | 立即 |

**实测收敛时间**（`POST /api/chaos/stop_and_rollback`）：

| 停止时机 | 收敛耗时 | 状态 |
|---|---|---|
| 场景 2 的**注入/保持期**（`app_memory_stress`） | **3.3s** 停止 + 17s 收尾清理 | `cancelled` |
| 场景 3 的**回滚阶段**（`app_kill_replica`，正在重启被杀容器） | 34.1s | `cancelled` |

> 第二行不是退步：`app_kill_replica` 的回滚动作本身就是"把容器重新拉起来"（10–30s），
> 这段**不应该也不能被取消** —— 取消了才真的会留下烂摊子。
> 所以"停止并回滚"的语义是：**立刻不再制造新故障，并把已造成的故障完整修好**。

停止后的终态（每次实测都验证）：

```
status = cancelled（不是 failed —— 用户主动停止不该显示红色失败）
step   = 已停止并回滚
result = {stopped_early: true, stopped_at: "场景 N/M 执行中（已回滚）", attempted: N/M}
active_faults = []
doctor = 15/15 PASS
busy = false
```

任务结束时**自动**执行 `cleanup_all()`（7 项：状态文件回滚 + 3 个应用副本 + 3 个 MySQL 节点），
不需要用户再点「紧急清理」。

#### 没有界面时怎么停（命令行兜底）

如果控制台不可用（或后端异常），两步即可复原：

```bash
# ① 停掉后台任务：演练循环跑在后端容器的线程里，重启即终止
docker restart rca-agent-backend

# ② 无状态兜底清理：不依赖 fault_state.json，按环境事实清除全部注入痕迹
python tools/fault_injector.py cleanup

# ③ 确认（应输出"总体: PASS"，且"无残留故障 OK"）
python tools/fault_injector.py doctor
```

`cleanup` 会清理：状态文件里的激活故障、应用容器内的 `stress-ng`、
MySQL 容器内的注入后台循环（按 `/proc` 标记扫描）、残留的长事务/等锁/Sleep 会话、
被改过的全局变量（`tmp_table_size` / `sort_buffer_size` / `join_buffer_size` / `max_heap_table_size`）、
被误置的主库只读、被误停的复制线程、被压小的 cgroup 内存上限。

> ⚠️ **注意**：`backend/` 是**挂载**进容器的（`./backend:/app/backend`），
> 且 uvicorn **没有** `--reload`，所以**改完后端代码必须 `docker restart rca-agent-backend`**
> 才会生效 —— 我这次就是这样踩了一次：新加的 `/stop_and_rollback` 路由返回 404，
> 而旧代码里的"取消"只记录不生效，等于没有停止按钮。

## 7. 压力测试（`tools/stress_harness.py`）

### 7.1 三种模式

| 模式 | 用途 |
|---|---|
| `http` | 打应用网关（默认 `POST /txn` 写主库；也可 `--path /txn/recent` 读副本） |
| `mysql` | 直连主库执行 SQL；`--mysql-hold-connections N` 让每 worker 长期持有 N 条连接 → **直接构造 `max_connections` 耗尽** |
| `mixed` | HTTP 与 MySQL 同时打，最容易构造"层间级联"故障 |

### 7.2 输出

* 成功率 / 错误分类 / 状态码直方图
* 延迟 min/p50/p90/**p95/p99**/max/mean（最近秩法，不插值，小样本不乐观）
* 吞吐 rps、字节率
* **分秒时序 `time_series`**（`{t, count, errors, p99_ms}`）—— 用于与故障窗口对齐，
  证明"故障窗口内确实劣化、回滚后确实恢复"

```bash
# 基线
python tools/stress_harness.py --duration 60 --concurrency 32 \
    --json-out .chaos/stress_baseline.json --label baseline

# 资源耗尽：4 worker × 60 连接 = 240 条，打满 max_connections=200
python tools/stress_harness.py --mode mysql --duration 60 --concurrency 4 \
    --mysql-hold-connections 60 --json-out .chaos/stress_conn_exhaust.json

# 混合压力（配合故障注入窗口）
python tools/stress_harness.py --mode mixed --duration 120 --concurrency 48 \
    --json-out .chaos/stress_mixed.json --label mixed-under-fault
```

## 8. 端到端验证智能体的诊断分析能力

`tools/cluster_rca_verify.py` —— 主程序。

### 8.1 流程（每个场景）

```
注入故障 → 后台压测放大 → 等待 Prometheus 采集与告警评估
   → 从 Prometheus 规则里取 firing/pending 告警的 rca_hint 作为告警文本
   → POST /api/agent/diagnose（deterministic / agentic / both）
   → 用 ground truth 给结论打分
   → 停压测 → 回滚 → 校验恢复 → 下一个场景
```

### 8.2 关键设计：不向智能体泄露答案

告警文本**不是**取故障目录里的描述，而是取监控系统真实生成的
`annotations.rca_hint`（`firing` 与 `pending` 都收）。智能体看到的信息与真实值班人员
看到的完全一致 —— 这同时验证了"告警规则 → 本体约束（`onto_constraint`）→ 智能体"
这条链路是否真的打通。

如果某场景一条告警都没触发，会退化为"监控无对应告警，但业务侧出现异常"，
并记 `alert_coverage = false` —— 这本身就是有价值的发现（说明该故障缺少告警规则）。

### 8.3 评分规则（ground truth）

期望根因来自 `tools/ontology_cluster_patch.py` 的 `SCENARIO_EXPECTED_TERMS`
（同一份映射也被本体演化的评估闸门复用）。命中判定（任一成立即 ok）：

| 判定 | 说明 |
|---|---|
| A. `root_cause.entity_id ∈ 期望 Term` | 最强证据：精确定位到本体根因术语 |
| B. 期望 Term 的 id/名称出现在候选/证据/推理摘要/工具观察文本中 | 允许"指认到正确实体但排序不同" |
| C. 场景语义关键词出现在同一段文本中 | 文本级回退（如"行锁""复制延迟""OOM"） |

同时记录：路由模式、HTTP 状态、耗时、token、工具调用、`how`（按哪种判定命中）。

### 8.4 用法

```bash
# 全部 21 场景（确定性快路径，秒级）
python tools/cluster_rca_verify.py --mode deterministic \
    --json-out .chaos/rca_diagnosis_report.json

# 只跑代表性的几个，走 LLM Agent（慢、耗 token，但验证真实推理）
python tools/cluster_rca_verify.py --mode agentic \
    app_oom_kill app_gateway_stop db_primary_readonly db_replica_lag \
    db_row_lock_hold app_pause_replica \
    --hold 80 --json-out .chaos/rca_diagnosis_agentic.json

# 两条路径同场景对比（确定性 vs Agent）
python tools/cluster_rca_verify.py --mode both app_kill_replica
```

### 8.5 模型设置：在界面上手动切换 LLM provider

**入口**：智能诊断页头部常驻显示当前模型（`🧠 agnes/agnes-3.0-flash`），
点旁边的 **⚙ 模型** 打开设置面板；手动覆盖时指示会变成
`🧠 rsxermu666/claude-opus-5-5 · 手动`（黄色）——**状态常驻可见**，
因为走哪个模型直接影响结论与 token 成本，不该藏在设置里。

**当前环境实测的 provider 可用性**（`/api/agent/llm/test` 逐个实测）：

| provider | 协议 | 默认模型 | Key 状态 | **实测连通性** |
|---|---|---|---|---|
| `agnes` | openai-completions | `agnes-3.0-flash` | ✅ 已配置 | ✅ **可用**（4.5–7s，80 tokens） |
| `rsxermu666` | anthropic-messages | `claude-opus-5-5` | ⚠ 存在但**已过期** | ❌ **HTTP 403「此 API Key 已过期」** |
| `deepseek` | openai-completions | `deepseek-chat` | ❌ 未配置 | ❌ 缺 Key |

> 也就是说：**当前真正在用的只有 `agnes`**；`rsxermu666` 的 Key 需要更新后才能在界面上切过去。

**能力**：选 provider（带 Key 状态）→ 选/改模型 → 可选填 API Key（password 输入）→
**🧪 测试连接**（不保存）→ **保存并切换** → **恢复默认**。

**四条边界（界面里也写明了，不留含糊）**：

1. **只对当前后端进程生效**，重启后端回到环境变量/compose 的配置；
2. 填入的 API Key **只存后端内存、不落盘**，读取一律脱敏（`sk-2g2n***`）；
3. 只能选后端**已注册**的 provider —— 不提供任意 base_url，
   避免把这个接口变成"让服务端向任意地址发请求"的 SSRF 通道（`POST /llm` 校验并返回 400）；
4. 「测试连接」**只试当前选中的 provider/model**，不走容灾链。

#### 实现这个功能时踩到的两个坑（都属于"绿灯在撒谎"）

**坑 1：容灾链让"测试连接"给出假绿灯。**
`LLMClient.chat` 的降级链是「主模型 → 同 provider fallback → **其它 provider**」。
第一版测试接口直接复用它，于是测 `rsxermu666`（claude）**返回 ok=True**，
但响应里的模型是 `agnes-3.0-flash` —— 真正干活的是**另一个 provider**，测试完全没回答问题。
**处置**：给 `chat()` 加 `strict_single=True`（只试 `(provider, model)` 一个组合），
测试接口用它，并把 `model_mismatch` 显式返回。
修完后同一个测试立刻如实报出 `HTTP 403: 此 API Key 已过期`。

**坑 2：`RCA_LLM_MODEL` 是全局环境变量，跨 provider 串味。**
compose 里写死 `RCA_LLM_MODEL=agnes-3.0-flash`；切到 `rsxermu666` 后，
该变量仍然生效 → 变成**拿着 agnes 的模型名去请求 claude 的端点**。
**处置**：运行中覆盖的 provider 与环境变量 provider **不同**时，忽略
`RCA_LLM_MODEL`/`RCA_LLM_BASE_URL`/`RCA_LLM_FALLBACK_MODEL`，改用新 provider 自己的默认值；
切 provider 时同时清掉旧的 model/base_url 覆盖。修完后切到 rsxermu666 显示 `claude-opus-5-5`。

#### 验证方式（真浏览器 + 真调用）

CDP 驱动实际点击（`tools/` 下的临时脚本，验证后已删）：

```
1) 头部指示 = 🧠 agnes/agnes-3.0-flash
2) 点击 ⚙ 模型 → 弹窗存在 = True
3) provider 列表 = agnes ✅sk-2g2n*** / rsxermu666 ✅sk-3YDF*** / deepseek ❌无 key
   弹窗定位 = fixed | 宽度 = 680px | 说明区加粗正常、无字面 `**`
4) 测试连接 = ✅ 成功 | agnes / agnes-3.0-flash · 4549ms · 80 tokens | 返回：正常
5) 选 rsxermu666 → 表单模型自动变为 claude-opus-5-5
   测试 = ❌ 失败 | HTTP 403 此 API Key 已过期
6) 保存并切换 → 头部指示 = 🧠 rsxermu666/claude-opus-5-5 · 手动
7) 恢复默认 → 头部指示 = 🧠 agnes/agnes-3.0-flash
8) 页面上是否出现完整 key = 无 ✅
```

**集成验证**（确认切换真的影响诊断链路，而不只是显示）：

| 步骤 | 生效配置 | 诊断实际使用模型 | 诊断耗时 |
|---|---|---|---|
| 默认 | `agnes/agnes-3.0-flash` | `agnes-3.0-flash` | 59.4s |
| 切到 `rsxermu666` | `rsxermu666/claude-opus-5-5` | `agnes-3.0-flash`（**容灾回落**） | 100.1s |
| 恢复默认 | `agnes/agnes-3.0-flash` | `agnes-3.0-flash` | — |

耗时从 59s 涨到 100s，正是因为**先按新配置去试 claude、失败后才回落** ——
这同时证明了两件事：切换对诊断路径生效；而**诊断路径上的容灾依旧保留**
（只有界面「测试连接」是严格单 provider，避免测试给出假绿灯）。

## 9. 本体迭代（验证本体的可扩展能力）

### 9.1 问题

环境已经集群化，而本体还是**单实例视图**：18 个 Term 里没有任何
"副本 / 集群 / 网关 / 只读副本 / 复制延迟 / CPU 配额 / OOMKill" 概念。
结果是 21 个集群故障场景里有 **20 个**在本体里既没有根因术语，
也没有"故障如何传播到症状"的路径，更没有"凭什么确认它"的可观测连接。

### 9.2 协议（严格走 EvoOntology 自演化，不直接改激活版本）

```
start_evolution_run(parent_version=<当前激活版本>,
                    acceptance={"protocol": "ground_truth"})      冻结预算与验收协议
  ↓
begin_evolution_round(hypothesis, candidate_version="ontology_v1-cluster")
  ↓
候选 = 父版本 5 族记录深拷贝 + 集群补丁（tools/ontology_cluster_patch.py）
     → SemanticStore.save_version(ws, candidate, records)
  ↓
validate(ws, version=candidate)                       交叉引用 / 可加载性（0 错误才继续）
  ↓
成对评估（同一批 case）
     record_evolution_evaluation(parent,    {metrics, cases}, role="parent")
     record_evolution_evaluation(candidate, {metrics, cases, gate_input}, role="candidate")
       gate_input = {protocol:"ground_truth", case_ids, parent_scores,
                     candidate_scores, unacceptable_regressions: false}
  ↓
accept_evolution(new_version="ontology_v1")
     validate → EvaluationGate.decide_gt → publish → set_active → advance_checkpoint
  ↓
finalize_evolution_run()  +  渲染多版本离线可视化 HTML
```

### 9.3 成对评估指标：本体可诊断性（structural diagnosability）

对每个故障场景 case，按给定版本的 5 族记录确定性复算，3 项等权：

| # | 要求 | 回答的问题 |
|---|---|---|
| ① | 期望根因 Term **已定义** | 本体里有没有这个词？ |
| ② | 该 Term 与用户可见入口（`app:payment-app` / `app:payment-app-cluster`）在关系图中 **≤4 跳连通** | "故障如何传播到症状"被建模了吗？ |
| ③ | 该 Term **可观测**（本身是 metric / 直接关联 metric / 是某条约束的 target） | "凭什么确认它"被建模了吗？ |

得分 = 满足项数 / 3。这是一份可复算的 ground truth，不依赖 LLM 打分，也不依赖主观判断。

### 9.4 用法

```bash
python tools/evolve_ontology_cluster.py --dry-run   # 只评估不发布（演练 + 出 Δ 报告）
python tools/evolve_ontology_cluster.py             # 完整执行并发布 ontology_v1
python tools/evolve_ontology_cluster.py --status    # 查看当前演化运行
```

### 9.7 闭环与反向迭代（第 1 轮 + 第 2 轮）

第 1 轮只解决"知识有没有"。要让本体真正改变引擎行为，还需要两步：

**闭环（引擎读本体）** —— 新增 `rca-agent/backend/services/ontology_scoring.py`：

```
打分词典(term) :=
    primary   = Constraint.trigger_keywords        # 人工精修，全权
              + Term.aliases / Term.id 词元         # 全权
              + Term.scoring_keywords               # ontology_v2 起
    secondary = Term.name 的中文 n-gram             # 半权，且按"最长命中长度"计
    negative  = Term.negative_keywords              # ontology_v2 起，命中扣分
    category  = 约束 target/scope → Term.scope → 邻居多数表决 → id 前缀
    role      = Term.role（root_cause/component/observation/rule）→ 权重
匹配方向 = 告警文本 ↔ 本体术语（**不是**术语 ↔ 自己的名字）
```

**反向迭代（引擎需求 → 本体扩展）** —— 第 2 轮 `ontology_v2`：

知识完备后 top1 仍只有 52%，因为"副本丢失 / 副本假死 / 副本 OOM / 副本被节流"
共享"副本"一词。这不是缺知识，而是**缺表达能力**：术语只能声明自己是什么，
不能声明"什么情况下不是我"。于是给 Term 增加三个字段：

| 字段 | 作用 | 例子 |
|---|---|---|
| `scoring_keywords` | 判别性正向词（比 name/alias 更贴近告警措辞） | `rc:replica-hang`: `假死`、`挂起`、`pause`、`端口在但不返回` |
| `negative_keywords` | 排除词（"我不是这个故障"的显式声明） | `rc:replica-loss`: `!假死`、`!pause`、`!节流`、`!内存` |
| `role` | 术语在 RCA 中的角色，决定权重 | `root_cause` 1.15 / `component` 1.00 / `observation` 0.85 / `rule` 0.80 |

同时新增 11 条管辖约束（`con:replica-loss-detection`、`con:db-cpu-capacity`、
`con:tmp-disk`、`con:fastpath-trust` …），让「哪个约束管这个根因」也进入本体 ——
既让类别推导有据可依，也让路由的 `favoured` 更精确。

> 这两步合起来才是"本体迭代能力"的完整验证：
> **环境变了 → 本体补知识（第 1 轮）→ 引擎学会用知识（闭环）→
> 引擎暴露精度不足 → 本体补表达力（第 2 轮）→ 引擎精度达标（§10.5）。**

### 9.8 第 3 轮：本体卫生（游离术语清理 + 缺失概念补齐 + lifecycle 声明）

**怎么发现的**：有人问"v2 里为什么有很多游离、没有任何关联关系的实体，比如『应用发布事件』？
什么场景会用到它们？" —— 这是**本体质量问题**，不是知识缺口问题，于是补了一个审计工具。

```bash
python tools/ontology_hygiene.py                 # 审计 + 闸门（PARAM 失败即 exit 1）
python tools/ontology_hygiene.py --version ontology_v2 --json-out .chaos/ontology_hygiene_before.json
```

**审计 `ontology_v2` 的结果**：

| 检查项 | 结果 |
|---|---|
| 引擎可见拓扑节点 | **49 / 51** |
| ① 游离术语（关系图度为 0） | **2 个**：`env:cluster`、`evt:deploy` |
| ② 从入口不可达 | 同上 2 个 |
| ③ 无证据支撑 | `api:auth`、`evt:deploy` |
| ⑤ 不可确认的根因 | **0 ✅** |
| ⑥ `lifecycle` 声明 | **51 个全部"未声明"** |

**根因**：`tools/init_evo_ontology.py`（首版 TTL→5 族转换器）**只映射了 TTL 对象属性的
一个子集**，漏了三个：

| TTL 语句 | 后果 |
|---|---|
| `:PayContainer :managedBy :DockerCluster` | `env:cluster` 游离 |
| `:PaymentApp :generatesEvent :DeployEvent` | `evt:deploy` 游离 |
| `:TTxn :hasIndex :IdxTxn*` | **索引个体根本没被建成 Term** |

只通过这三个属性连接的个体全部掉出关系图。

**"什么场景会用到"——逐条链路验证**：

| 链路 | 会不会用到 | 依据 |
|---|---|---|
| 确定性引擎（候选根因） | **不会** | 引擎拓扑只有 49/51，这 2 个不在其中 |
| 场景覆盖 / 诊断评分 | **不会** | 19 个期望根因术语全部可达、游离 0 个 |
| 图谱推理（传播路径） | **不会** | 度=0，没有可遍历的边 |
| **LLM Agent 语义检索** | **会，而且是噪声** | 实测 `browse_semantics('发布 变更 deploy 上线')` **唯一返回的就是 `evt:deploy`**；`resolve_semantics` 对它和 `env:cluster` 都返回 `coverage_status=partial` + `evidence_refs=[]` |

结论：**诊断链路一次都用不到；唯一浮出水面的地方是 Agent 的语义检索，在那里它是纯干扰项**
——Agent 可能据此声称"本体认识发布事件"，但既没有 Mapping（拿不到部署数据源）
也没有 Evidence（无可复现观测），引用无法落地。**本体规模 ≠ 本体能力。**

**第 3 轮做的三件事**（`tools/ontology_v3_patch.py`，走完整自演化协议 → `ontology_v3`）：

1. **把游离术语真正用起来**
   * `evt:deploy`：补 `generatesEvent` 关系接到应用；新增可观测的部署时间源
     `metric:uptime-since-deploy`（容器镜像 ID + `State.StartedAt`，模拟环境没有 CI 事件源，
     这是唯一可离线复算的时间依据）；新增 `con:change-correlation`，
     让**"是不是发布引入的"成为本体可推理的问题**（这正是种子问题集里的一条）。
   * `env:cluster`：补 `managedBy` 关系接回主图；**改名消歧**
     （"Docker 容器运行时引擎（非业务集群）"，定义里显式写明它与
     `app:payment-app-cluster`、`db:mysql-cluster` 的区别），并加负向词阻止"集群"撞车。
   * 索引：补 `idx:txn-created` / `idx:txn-customer` 两个 Term + `hasIndex` 关系 +
     接地到 `information_schema.statistics` + `con:index-usage`，
     把"慢查询是不是索引缺失"这一环补上（实测索引：
     `idx_txn_created(created_at)`、`idx_txn_customer(customer_id)`、`PRIMARY(txn_id)`）。
2. **声明 lifecycle**：54 个术语全部声明（已接线且可观测 → `active`）。
   契约规定：**未接线的术语必须标 `draft`**，EvoOntology 运行时只在 `validated`/`active`
   时参与查询，所以 `draft` 术语不会再污染语义检索 —— 这套机制以前一次都没用上。
3. **加闸门**：`EvolutionSession.accept()` 之前先跑 `ontology_hygiene.gate()`，
   违反以下任一条即拒绝发布（`session.mark_incomplete("unreliable_evaluation")`）：
   * 期望根因术语游离/不可达
   * 未声明 lifecycle
   * 声明 `active` 却游离
   * 存在不可确认的根因（无 metric 关联且非约束 target）

**结果**：游离 0 / 不可达 0 / 不在拓扑 0，lifecycle 54/54 `active`，
卫生契约 **0.699 → 1.000**（提升 54 case、0 回归），
**引擎 top1 与 top5 持平（20/21、21/21，无回归）** —— 卫生轮的设计目标就是这个。

**生成器已同步修复**：`init_evo_ontology.py` 补上三个属性的映射与索引个体，
并新增**写前归档**（覆盖已存在的版本目录前先归档到
`.evoontology/archive/<version>-<UTC 时间戳>/`）。
重建基线后 `ontology_v0` 的关系数由 20 → 25、游离术语 0 个。

> ⚠️ 开发过程中确实误用 `--force` 原地覆盖过一次 `ontology_v0`（本体版本本应是不可变历史），
> 这才加的写前归档。当前 `ontology_v0` 是**用修复后的转换器重建**的版本，

### 10.6 一键流水线与"证据新鲜度"

**为什么需要它**：在这之前复现全量证据要手工按顺序跑 5~6 个脚本（21 场景注入约 40 分钟），
容易漏步、顺序错，或者**拿过期产物当当前结论** —— 本项目真实发生过：
`fault_verify_report.json` 里的"21/21"产出于改动注入实现（`sleep`→`wait`）**之前**，
却被当成当前代码的能力证据。所以流水线除了串流程，还针对这个教训做了三件事：

| 机制 | 作用 |
|---|---|
| **代码指纹** | 对 13 个关键实现文件（catalog / core / 引擎 / 告警规则 / compose…）算摘要并写进报告。读者第一眼就知道"这份报告对应哪一版代码" |
| **产物新鲜度** | 记录每个产物 mtime 并与本次运行开始时间比对，标 `fresh` / `⚠ 本次未更新`。旧文件没被覆盖 = 结论可能是旧的 |
| **finally 必跑 cleanup** | 无论中途失败还是 Ctrl+C 都回滚（"清理是安全网"这条不变式本项目已被违反过一次，见 §11.17） |

**步骤顺序不可随意调换**：

```
doctor（环境干净）→ 本体卫生 → 打分 A/B → 21 场景故障验证
→ 处置动作有效性 → 压测基线 → 端到端注入→诊断 → cleanup（finally）
```

`doctor` 必须最先（环境不干净时后面所有数字都无意义）；破坏性步骤排在读类步骤之后。
流水线结束时打印汇总表（每步状态/耗时/产物新鲜度）并输出
`.chaos/run_all_verification.json`；任一**必需**步骤失败即整条判 FAIL。

## 11. 进展、仍存在的问题与下一轮目标

本轮验证刻意保留"不粉饰"的结论。上一版报告的三个瓶颈里，**两个已在本轮修掉**，
第三个仍然存在 —— 下面分别给出修复方式与量化结果。

### 11.1 ✅ 已解决：确定性引擎的打分词典改为本体驱动（原发现 A）

**问题**：`rca_engine.category_keywords` 是代码内置关键词表，
本体迭代把知识完备性从 0.048 拉到 1.000 后，候选命中只从 top5 1/21 提升到 4/21 ——
**知识躺在库里，改不动引擎行为**。

**修复**（`rca-agent/backend/services/ontology_scoring.py`，新增 ~430 行）：

| 环节 | 做法 |
|---|---|
| 词典来源 | `Constraint.trigger_keywords` + `Term.aliases/id` 词元（全权）＋ `Term.name` 中文 n-gram（半权）− `negative_keywords` |
| 匹配方向 | **告警文本 ↔ 本体术语**（原实现是术语 ↔ 自己的名字，会必然自匹配、退化成按类别排序） |
| 中文 n-gram 计权 | 按**最长命中 n-gram 长度 × 0.5**，不按命中个数（否则"应用副本"会被 2/3/4-gram 重复计 6 次） |
| 节点类别 | 约束 target/scope 的 `constraint_type` → `Term.scope` → 邻居多数表决 → id 前缀 |
| 节点角色 | `Term.role`（root_cause/component/observation/rule）→ 权重 1.15/1.00/0.85/0.80；缺失时按 id 前缀推导 |
| 路由 favoured | 告警命中的本体约束的 `constraint_type` 与 target 类别的并集 |

**结果**：top5 命中 **1/21 → 21/21**，top1 **1/21 → 20/21**（§10.5）。

### 11.2 ✅ 已解决：双引擎路由不再过度自信（原发现 B）

**问题**：`router.KNOWN_ROOT_CAUSES` 硬编码含 `rc:slow-sql`（置信度 0.83 ≥ 放宽门槛 0.75），
`--mode auto` 下 4/4 集群故障全部落在快路径并返回同一个过期根因，**Agent 从未获得机会**。

**修复**（`router.py`）：

1. `KNOWN_ROOT_CAUSES` 从本体派生（`rc:` 前缀的 entity 术语），不再硬编码；
2. 新增**约束支撑度**判定：规则引擎给出的根因实体必须是某条「被告警文本命中的本体约束」的
   `target`，或在其 **2 跳邻域**内、类别一致；
3. 不被支撑、且存在指向别处的约束命中时 —— **强制交 Agent 复核**，
   并在 `route.reason` 里写清命中了哪条约束、指向哪个 target；
4. 把"快路径采信条件"本身也写成一条本体约束（`con:fastpath-trust`），
   下次再改路由策略就有本体记录可审。

**结果**：快路径从「4 例、全部无支撑」变为「21 例、全部被约束支撑、top1 精确率 **95%**」。

### 11.3 ✅ 已实质解决：Agent 的最终根因实体落回本体术语（原发现 C）

> **状态更新（2026-10-08）**：本节记录的是**当时的发现**（严格命中 0/24）。
> 该问题现已实质解决 —— 全量 21 场景重测：**严格 17/21（81%）**（§11.25）、
> 完整链路那轮 **11/21（52%）**，其中**有告警文本的子集 11/14 = 79%**（§11.26）。
> 两个口径的差距来自**输入可得性**（无告警文本时引擎近似空手），不是引擎退化。
> 下面保留原始记录以便回溯。

强制 `--mode agentic` 后，Agent 的推理摘要与证据文本里已经出现正确概念（宽松命中可观），
但 `root_cause.entity_id` 在 **24** 次运行中只有 **0** 次等于期望的本体 Term（严格命中 0%）——
它是在**确定性先验给的候选集**里挑，而不是把推理结论映射回本体 Term；
`db_replica_lag` 甚至返回过 `env:container/rca-agent-payment-app-*` 这种本体里不存在的拼接 id。
另外 3 次 agentic 调用因 LLM 未返回结构化 JSON 而回退为确定性结论，3 次触达步数/时间预算。

> **下一轮**：① Agent 收尾时约束 `root_cause.entity_id` 必须取自
> `browse_semantics` / `resolve_semantics` 返回的 Term id（受约束解码 + 校验失败重试）；
> ② prompt 里减弱对确定性先验的绑定，让 seed 真正只是"先验"；
> ③ LLM JSON 解析失败时重试而不是直接 fallback。

### 11.4 本轮新踩到的坑（都已修）

1. **中文 n-gram 不能按命中个数计权**。初版把 `应用副本` 同时命中的 2/3/4-gram
   （应用、用副、副本、应用副、用副本、应用副本…）算成 6 次命中，同一段文字被重复计分，
   把不相关的根因顶到第一；改成"最长命中 n-gram 长度 × 0.5"后 3 个 case 立刻转正。
2. **遍历上限必须随本体规模上调**。本体从 18 → 51 个 Term 后，线上拓扑 BFS 仍是
   40 节点 / 4 跳，把 `rc:row-lock`/`rc:tmp-disk` 这类深度靠后的根因术语**直接截掉** ——
   离线 A/B 20/21、线上却只有 15/21，**差距全部来自这里**。
   已上调为 160 节点 / 6 跳（首次 BFS 约 15s 建缓存，之后命中进程内缓存）。
3. **过度宽泛的负向词会反噬**。`rc:db-replica-loss` 的排除词里写了 `只读`，
   但"只读副本"正是它的合法表述 → 被扣分；改成 `置为只读` / `read_only` 后转正。
   同类问题还有 `con:db-role`（主库只读）的 `只读` 关键词污染了 `db:primary` 的词典，
   已在组件术语上用负向词排除。
4. **本体需要"这是根因"的语义**。`metric:db-tmp-disk`（观测）会压过 `rc:tmp-disk`（根因），
   `db:mysql-replica`（组件）会压过 `rc:replica-lag`（根因）—— 这是 `role` 字段出现的直接原因。

### 11.5 其他限制

1. **`scoring_keywords` / `negative_keywords` / `role` 是对 EvoOntology Term schema 的扩展**
   （`validate()` 只强制 `id`，额外字段可安全共存；运行时忽略未知字段）。
   若上游要正式支持，建议纳入 schema 文档。
2. **负向词是人工编写的，存在过拟合到当前 21 个场景的风险**。
   `res_cluster_memory` 仍判为 `rc:oom-kill` 而非 `rc:cluster-capacity` ——
   该场景描述本身写着"全部副本面临 OOM Kill 风险"，两个答案都说得通；
   本轮**不为了凑满分去改 ground truth 标签**，如实记为未命中。
   下一轮必须用新场景（held-out）复验，避免退化成"换个说法的硬编码"。
3. **LLM Agent 路径评估成本高**（每场景 30–200s），端到端验证在 12 个代表性子集上采集。
4. **副本实例接地是静态声明**：`app:instance-1..3` 的映射在副本扩缩容后需要重新接地。
5. **网络类故障缺少包级证据**（未部署抓包/连接追踪）。
6. **资源配额阈值是演示值**（应用 0.5 CPU / 256MB），生产需按容量规划重标定。
7. **容器内工具差异导致的回滚陷阱**：
   * `mysql:8.0` 镜像基于 Oracle Linux，**没有 procps**（`ps`/`pkill`/`pgrep` 全缺）；
     早期版本用 `pkill -f <pattern>` 回滚，命令静默失败（`2>/dev/null; true` 还返回 0），
     注入循环继续跑 → 4 个场景"回滚后信号不消失"。改为扫 `/proc/*/cmdline` +
     `kill -9`（标记值经环境变量传入，避免自杀）。
   * **`processlist.info` 不保留 SQL 注释**，服务端兜底不能用注释匹配会话，
     只能用 `command`/`state`/`time` 这类真实字段。
   * **`Threads_running` 基线不为 0**：主库 ≈5（含 2 个 Binlog Dump 线程）、副本 ≈2，
     用 `max(threads_running) > 2` 会恒为真 —— 必须限定 `db_node="primary"` 并抬高阈值。
   * **`ORDER BY` 不产生临时表**：filesort 不增加 `Created_tmp_disk_tables`，
     必须带 `GROUP BY` 才会生成（内部）临时表；且单循环速率不够，需要并行放大。
   * **CPU 节流计数器恒 > 0**：轻载下 `rate(nr_throttled_total[1m])` ≈ 0.02~0.07，
     用 `> 0` 做恢复校验会永远判定"未恢复"，必须用**量级阈值**（实测故障期 ≈ 3s/s 节流时间）。

### 11.6 ✅ 已解决：本体里的游离术语与"虚高覆盖率"（第 3 轮）
**问题**（提问式发现）："v2 里为什么有很多游离、没有任何关联关系的实体，
比如『应用发布事件』？在什么场景会用到？"

**审计结论**：不是"很多"，是 **2 个**（`env:cluster`、`evt:deploy`）；
根因是首版 TTL→5 族转换器**漏映射了 3 个对象属性**
（`managedBy` / `generatesEvent` / `hasIndex`，其中 `hasIndex` 导致索引个体连 Term 都没建）。
它们**在诊断链路里一次都用不到**（不在引擎拓扑、不在期望根因集、无 Mapping 无 Evidence），
唯一浮出水面的地方是 **LLM Agent 的语义检索，而那里它是噪声**：
`browse_semantics('发布 变更 deploy 上线')` 唯一返回的就是 `evt:deploy`，
但 `resolve_semantics` 只给出 `coverage_status=partial` + 空证据。

**修复**（第 3 轮 `ontology_v3`，详见 §9.8）：把三个概念真正接线
（`evt:deploy` 接入变更关联链条并给出可观测的部署时间源、`env:cluster` 补 `managedBy` 并改名消歧、
索引补成可接地术语），54 个术语全部声明 `lifecycle`，
并在 `accept` 前加**卫生闸门**。
结果：**游离 2 → 0、不可达 2 → 0、不在拓扑 2 → 0、卫生契约 0.699 → 1.000，
引擎 top1/top5 不回归**。生成器也同步修好（并新增写前归档），重建基线即为 0 游离。

**剩余的非阻断告警**：`api:auth` 声明 `active` 但无证据、且模拟环境里并未实现该接口 ——
建议下次触碰本体时改标 `lifecycle.state=draft`（该检查已作为 gate 的 `warnings` 常驻）。

**一条教训**：**版本目录必须是不可变历史**。开发中误用 `init_evo_ontology.py --force`
原地覆盖过一次 `ontology_v0`；`--force` 只拦住了"无参数重跑"，没拦住"强制重跑后的原地覆盖"。
已改为**写前归档**到 `.evoontology/archive/<version>-<UTC 时间戳>/`。
当前 `ontology_v0` 是重建版，第 1 轮的父版本参照线用的是未被触碰的 `ontology_v0-rca-agent`，
历史评估记录不受影响。

### 11.7 ✅ 已解决：批量演练停不下来（原设计缺陷）

**问题**（用户误点后暴露）：控制台的「批量演练」是一键触发的破坏性操作，
但当时的"取消"实现只往日志里写一句话、**不产生任何效果** ——
点了不知道去哪停，演练会一路跑完 21 个场景（20–40 分钟）。

**根因有三层**，缺一层都会表现为"停不下来"：

| 层 | 问题 | 修复 |
|---|---|---|
| 语义 | 取消只是打日志，没有取消点 | 引入 `cancel_event` + **协作式取消**：注入等信号 / 压测期等信号 / 保持期 / 停压测宽限期 / 场景间隔 / 恢复校验，**每处阻塞都接了取消回调**（详见 §6.6 的取消点表） |
| 一致性 | **不强杀线程**（避免半注入），但当时也没承诺"取消后必定回滚" | 立下不变式：**无论取消/异常/正常结束，`run()` 与 `verify_scenarios()` 都必定执行回滚**；`verify_scenarios` 用 `try/finally` 兜底 `recover_all()` |
| UI | `busy` 只在本页提交任务时为真 → **刷新页面或从别处启动的任务看不到停止按钮**（等于没有出口） | 改为派生状态 `running = busy \|\| job.status ∈ {running, queued}`；挂载时**接管**服务器上仍在跑的任务；5s 轮询发现"别处启动的任务"也自动接管 |

**实测**：

| 停止时机 | 收敛耗时 | 说明 |
|---|---|---|
| 场景 2 的注入/保持期 | **3.3s** 停止 + 17s 收尾清理 | 取消点密度足够 |
| 场景 3 的回滚阶段（`app_kill_replica` 正在重启容器） | 34.1s | 这段是**回滚本身**，不该也不能被取消 |

停止后终态：`status=cancelled`（不是 `failed`）、`active_faults=[]`、`doctor 15/15`、`busy=false`。

**顺带修掉的两个"证据安全"问题**：

1. **子集运行静默覆盖全量证据**：用 `--only app_memory_stress` 做一次回归，
   就把 21/21 的 `fault_verify_report.json`（137KB）覆盖成了 1/1 ——
   报告里"故障注入自检"整节会瞬间变成假数据。
   现在按范围分开落盘：子集写 `fault_verify_report_subset.json`，并在产物里标 `scope`。
2. **后端代码改动需要 `docker restart`**：`backend/` 是挂载进容器的，
   而 uvicorn **没有** `--reload`。新加的 `/stop_and_rollback` 路由因此一开始返回 404，
   表现为"停止接口不存在"。已写进 §6.6 的兜底步骤里。

### 11.8 ✅ 已解决：应用副本堆积 `stress-ng` 僵尸进程

**问题**：跑几轮演练后，应用副本里堆了 `stress-ng` 的 `<defunct>` 进程
（实测单副本 26 个）。它们**不占 CPU/内存**，但会：
· 污染"进程计数"类判断（`pgrep -fc stress-ng` 会把僵尸算进去，让人误以为压测还在跑）；
· 白占 `pids_limit: 512` 的名额，极端情况下耗尽 PID。

**根因**：容器的 **PID 1 是 `node`**，而 node 不会 `wait()` 非自己 spawn 的子进程 ——
注入器 `docker exec` 进容器起的 `stress-ng`，其后代在父进程退出后无人回收。

**修复**：给 `payment-app` 加 `init: true`（Docker 注入 tini 作为 PID 1，负责回收孤儿/僵尸）。
`pids_limit` 与 `cgroup` 限额不受影响。

**验证**：重建 3 副本后 `PID 1 = /sbin/docker-init`、`node server.js` 降为 PID 7；
跑完 4 个"进程密集 + 杀容器"场景（`app_cpu_stress` / `app_memory_stress` /
`app_oom_kill` / `app_kill_replica`，**4/4 通过**）后，
三个副本的 `defunct=0`、残留 `stress-ng=0`（改前同一批场景会堆 26 个僵尸）。

### 11.9 ✅ 已解决：两条"恒真/恒假"的信号让校验形同虚设

**怎么发现的**：误点演练后我复跑了完整 21 场景，`db_slow_query_flood` 与 `res_db_memory`
报 `error: None`（`ok=False` 但没有错误文本 → 说明是**恢复校验超时**，不是注入失败）。
进一步量基线才看清问题：

```
# 环境完全空闲（无故障、无压测）时
rate(mysql_global_status_slow_queries[1m])  三个节点均 ≈ 0.0222/s
rate(...{db_node="primary"}[2m])            主库 ≈ 0.24/s
```

**根因**：`long_query_time = 0.1s` 非常激进 —— 应用自身的读查询、
甚至我们自己的 `SELECT COUNT(*) FROM t_txn`（30 万行）都会被记成慢查询。
于是 `slow_queries` 的**空闲基线不为 0**。而这两条场景写的是：

| 场景 | 原注入信号 | 原恢复信号 | 后果 |
|---|---|---|---|
| `db_slow_query_flood` | `rate(slow_queries[2m]) > 0` | `rate(slow_queries[1m]) > 0` | 注入信号被基线满足 → **恒真，等于没校验**；恢复信号**永远不可能变假** → 随机"回滚失败" |
| `res_db_memory` | `... > 0`（其二） | `rate(slow_queries[1m]) > 0` | 同上 |

之前 21/21"通过"其实靠的是**采样的运气**：`[1m]` 窗口偶尔恰好没有样本，
`expect="falsy"` 把"无样本"也算成立。**这比失败更危险 —— 它给出的是假阳性证据。**

**修复**（`tools/chaos/catalog.py`）：阈值抬到基线之上，并把校验**限定在注入的主库**
（避免副本回放/噪声串进来）：

| 场景 | 新注入信号 | 新恢复信号 |
|---|---|---|
| `db_slow_query_flood` | `max(rate(slow_queries{db_node="primary"}[2m])) > 0.45` | `max(rate(slow_queries{db_node="primary"}[1m])) > 0.45` |
| `res_db_memory` | `max(rate(created_tmp_disk_tables{db_node="primary"}[2m])) > 0.1` | `max(rate(created_tmp_disk_tables{db_node="primary"}[1m])) > 0.1` |

阈值依据实测：主库 `slow_queries` 空闲 ≈0.24、本故障期 ≈0.69 → 取 0.45（两侧 1.5–1.9 倍余量）；
`created_tmp_disk_tables` 空闲 ≈0.019、故障期 ≈0.19 → 取 0.1（与既有的
`db_disk_temp_tables` 同款写法，那条一直是"高于基线"的正确示范）。

**顺带修掉两处配置漂移**：

1. **压测强度**：`verify` 的 `--stress` 默认值是 `60s×24`，而文档 §10.2 的验证命令显式传
   `20s×12` —— 同一套场景用不同负载会得出无法对比的结论。
   现在统一为 `DEFAULT_VERIFY_STRESS = "--duration 20 --concurrency 12"`，
   控制台的「批量演练」也用这一配方。
2. **恢复预算**：部分恢复校验是 `rate(...[1m])`，需要等这一分钟窗口把故障期数据排出，
   80s 会偶发超时 → 统一到 110s。

**修复后重跑完整 21 场景**：**21/21 通过**（`scope=full`），
其中 `db_disk_temp_tables` 112.6s、`db_slow_query_flood` 69.7s、`res_db_memory` 141.4s。
这次是**有判别力的校验**跑出来的 21/21，而不是恒真信号堆出来的。

### 11.10 ✅ 已解决：诊断台的两个界面缺陷（推理不进对话 / 拓扑空白）

**问题 1：聊天框只显示"我问了什么"，推理过程只在右侧面板**

推理本身就是对话的一部分，分屏显示让人感觉像自问自答。
修复办法不是"把面板挪个位置"，而是**让推理成为对话里的消息**：

| 改动 | 说明 |
|---|---|
| 新增 `ReasoningInline` 组件 | 与气泡同宽、可折叠；**同一个组件**既渲染流式中的实时推理，也渲染历史消息里保存的推理快照 |
| 流式期间 | 提问后立刻在对话末尾出现「推理过程（推理中…）」气泡，随 `reasoning` / `tool_call` / `observation` 事件实时增长 |
| 结论落地 | `final` 到达后把**推理快照存进 `ChatMessage.trace`**，并追加一条 assistant 消息（根因/置信度/证据/建议动作）；因此**历史每一轮都能展开回看当时的推理** |
| 右侧面板 | 去掉「🧠 推理」标签页（已移入对话），保留 RCA / 拓扑 / 指标 / 历史 |
| 快路径也要有推理 | 确定性快路径**不发 `step_*` 事件**、`steps` 一直是空的 → 后端 `orchestrator._fastpath_steps()` 把引擎**已经算过**的中间结果如实摆出来（本体匹配 → 候选打分 → 阈值核对 → 结论 → 路由判定），实测 **9 步**；前端再加 `normalizeSteps()` 兜底（final 里的 `tool_input`/`observation_ok` → 视图层的 `tool_args`/`ok`） |
| 文案按模式区分 | agentic 显示「N 次工具调用」，快路径显示「N 项证据核对」；步骤徽章改用文字（观察/推理/核对）而不是 emoji —— 无 emoji 字体时会渲染成小点 |

**问题 2：右侧「拓扑」永远是空白**

根因在**后端**：`/api/agent/diagnose` 的最终事件里**根本没有拓扑字段**。
`AgentResult` 没有 `topology/topology_edges/root_cause_path`，`_deterministic_result()`
只从 `seed["topology"]` 提取了 `affected_entities` 就把拓扑丢掉了 ——
而种子引擎 `RCAEngine.infer()` 其实一直算出了完整拓扑（54 节点 / 82 边）。
前端 `nodes=[]` → `TopologyGraph` 在 `nodes.length === 0` 时直接 return → 空白。

修复：`AgentResult` 补三个字段并纳入 `to_dict()`；确定性路径从 seed 填充，
Agent 路径也把 seed 的拓扑带上（两条路径都有拓扑）。

**顺带修掉的"有了但看不全"**：详情栏很窄（~230px），力导向布局的节点会飞出
SVG 之外。加了 `fitView()`（布局收敛后按节点包围盒反解 zoom 变换）、
`scaleExtent` 下限从 0.4 降到 0.1（否则 54 节点需要的缩放比被卡住，仍然溢出）、
窄栏时收敛斥力/边长、`alphaDecay` 调快（默认要 ~5s 才收敛，用户点开标签页看到的
正是"还在飞"的中间态）并加兜底定时适应。

**验证方式**：用 CDP 真实驱动一次诊断（填入问题 → 点发送 → 等结论 → 展开推理 → 切标签页），
断言"聊天里存在推理块且步骤数 > 0"与"节点渲染包围盒落在 SVG 可视区内"：

```
① 推理在聊天框 = PASS（展开后 9 步，徽章 ['确定性快路径', '2 项证据核对']）
② 拓扑有内容且未被裁切 = PASS
   拓扑渲染 = {circles: 55, lines: 82, text: 110,
               transform: "translate(27.2,135.8) scale(0.655)",
               overflowLeft: -4, overflowRight: -4}
   SVG 区域 = [1410,247,1670,947]  节点包围盒 = [1414,465,1666,729]
```

> 测试脚本本身也踩了一个坑，值得记下来：**同一个 CDP 页面里 `Page.navigate` 到相同 URL
> 不会真正重新加载**，于是页面一直跑着旧 bundle，新构建的前端"看起来没生效"。

### 11.11 ✅ 已解决：指标面板的数据准确性问题（4 个真实缺陷）

**①b 面板能打开了，但每个面板都是 "No data" + 红色报错三角**

修好 JSON 后截图验证，8 个面板标题与布局都正常，**但全部显示 "No data"**。根因是**接线错**：

```
数据源 provisioning 没写 uid → Grafana 自动分配 uid = PBFA97CFB590B2093
面板里写的却是            → "datasource": { "type": "prometheus", "uid": "prometheus" }
                          → 解析不到数据源 → 所有查询失败
```

面板文件合法、数据源也在、Prometheus 也健康，只是两者 uid 对不上。
这类问题只表现为"监控没有数据"，极易被误判成"服务没上报"。

重启 Grafana 后 API 确认 uid 已对齐、通过它查询返回 11 条 series，面板全部出数
（HTTP P99 均值 0.0091s、连接上限 10、内存 RSS 51.3 MiB）。

![Grafana 面板](images/Grafana_面板.png)

**② 行锁 P1 告警用漂移型 gauge → 环境干净却一直 firing**

```
规则（旧）: mysql_global_status_innodb_row_lock_current_waits > 0   → primary 恒为 1，持续 firing
实际状态  : information_schema.innodb_trx = 0，sys.innodb_lock_waits 为空 → 没有任何事务在等锁
```

根因：`Innodb_row_lock_current_waits` 靠"等待结束时递减"维护，而故障注入/回滚是**直接 KILL 会话**，
等待被中断时那次递减会漏掉 → gauge **永久卡在 1**（`SET GLOBAL` 重置无效，只能重启 MySQL）。

后果不只是"告警吵"：它会把 RCA 引向一个**不存在的行锁故障**，也会污染演示。

修复：改用只增计数器 `Innodb_row_lock_waits` 的**速率**（只反映"有没有**新的**等待"）：
`rate(mysql_global_status_innodb_row_lock_waits[2m]) > 0.05`（实测空闲 0.000 / 注入时 0.190，两侧余量充足）。
改完告警立刻归零，而那个漂移 gauge 仍显示 1 —— 正好证明新规则不受它影响。

**③ 连接池三个指标恒为 0（`active`/`idle`/`waiting`）→ 一条"恒为绿"的 RCA 证据**

mysql2 升到 **3.24.5** 后，`_allConnections` / `_freeConnections` / `_connectionQueue`
变成自定义 **`RingQueue`**（有 `.length` 但不是 `Array`），而应用代码写的是 `Array.isArray(...)` →
三个 gauge **永远 0**，且异常被 `catch` 静默吞掉。

危害在于它是 RCA 的证据来源之一：判定式 `cc_mysql_pool_active / cc_mysql_pool_limit > 80%`
**永远算出 0%**、永远不触发 —— 一个"恒为绿"的观测比没有观测更危险，因为它看起来像"查过了，确实没问题"。
（LLM Agent 的第一次观察就是 "连接池 0/0"，结论对，但证据无意义。）

修复：`_len()` 兼容 `Array`/类数组/`Set`；把三个 gauge 改成 **`collect()` 在抓取时求值**
（聚合写池 + 全部副本池），不再依赖"有没有走过写路径"——
原先 `updatePoolMetrics` 只在写路径调用，只服务读请求的副本连 `limit` 都报 0。
另外新增 **`cc_mysql_pool_metrics_ok`**：内部结构读不到时明确报 0，
让"指标不可信"这件事本身可见，而不是伪装成 0。

验证：未使用连接池时 `active=0/idle=0/metrics_ok=0`（如实说"不可信"）；
一次读请求后 `idle=1/metrics_ok=1`（真实值）。

### 11.17 ✅ 已解决：僵尸进程这一类问题（只修了"实例"没修"类"）

**发现方式**：验证压测的「停止」时，一次 `cleanup` 花了 **75.6s** 且中途只有 1 行日志，
看起来像"停止按钮没用"。查下去发现根因完全在别处：

```
cc-mysql-core      /proc 条目 = 1773  僵尸 = 1769（mysql=1640, sh=124, sleep=5）
cc-mysql-replica-1 /proc 条目 = 4     僵尸 = 0
cc-mysql-replica-2 /proc 条目 = 4     僵尸 = 0
```

**根因**：注入会在容器里起 `sh` 后台循环（`db_slow_query_flood` 等）；
回滚时 `kill_by_marker` 用 `kill -9` 杀循环外壳，**在飞的子进程（`mysql` 客户端）被孤儿化**，
reparent 到 PID 1；而 mysqld 作为 PID 1 **不回收任意孤儿** → 永久僵尸。

**我之前修过一次同类问题，但只修了 `payment-app`（那一次是 stress-ng 的僵尸）**，
没意识到"凡是会跑注入子进程的容器都需要 PID 1 能回收"。
这次把 `init: true` 补到 3 个 MySQL 容器（并在 compose 里写清原因）。
重建后：**全容器僵尸 0，PID 1 = `docker-init`**，主从复制与 doctor 全 PASS。

**连锁效应（为什么它不只是"难看"）**：清理脚本按标记扫 `/proc` 是 **O(进程数)**，
条目从 ~10 涨到 1769 → 每条 `docker exec` 从 <1s 变成 **9.92s** → 整体清理 17s → **75.6s**。
两个修复：

* **`kill_by_marker` 由"每 PID fork 一个 `cat`"改成单次 `grep -l -a`**
  → 同一条命令 **9.92s → 0.12s（83×）**。自身安全依旧：glob 先于 grep 的 fork 展开，
  且脚本里只有 `$CHAOS_MARK` 字面量、不含标记值，所以不会自杀。
* 僵尸清零后整体清理 **75.6s → 6.4s（12×）**。

**顺带修掉一个更坏的东西：体检脚本的假阴性。**
我此前用 `ps -eo stat | grep -c '^Z'` 统计僵尸并报告"全部为 0 ✅"——
但 `mysql:8.0` 镜像**根本没装 procps**（`sh: ps: command not found`），
命令失败被当成了 0。**假阴性比不做检查更坏**。
现在 `doctor` 增加 `容器无僵尸进程` 检查，实现只依赖 shell + grep 读 `/proc/<pid>/status`，
与镜像是否装 procps 无关；实测能准确报出 `FAIL cc-mysql-core=1769(mysql=1640, sh=124, sleep=5)`。

### 11.18 ✅ 已解决：卡住的任务会把控制台锁死（新增"强制解除占用"）

协作式取消依赖任务自己在取消点检查 `cancel_requested`。

把当前任务标记为失败并**释放单飞锁**。响应里明确写清代价 ——
**worker 线程可能仍在收尾，之后可能与新任务短暂并发** —— 所以它只是最后的出口，不是常用按钮。

### 11.20 ✅ 已解决：根因结论"太精简"（信息在链路上被**静默丢弃了三次**）

**起因**：用户反馈"RCA 结论太精简，比如：⚡ 根因结论，资源类，rc:tmp-disk"。
只有"类别 + 术语代号"确实等于什么都没说 —— 用户看不出**这是什么、机制如何、落在哪个实例上、凭什么判的**。

关键认识：这些信息**本体里本来就有**，不需要新写知识，只是没被取出来用：

| 结论要素 | 本体来源 |
|---|---|
| 可读名称 | `Term.name`（"根因：排序内存不足导致磁盘临时表"） |
| 机制 | `Term.definition`（"tmp_table_size / sort_buffer 偏小，GROUP BY/ORDER BY 溢出到磁盘临时表"） |
| 归因对象（落在哪） | 关系里 `attributedTo:` 前缀（`rel:rc-tmp-disk-attributed` → `db:primary` 主库节点） |
| 观测佐证 | 关系里 `evidencedBy:` 前缀（→ `metric:db-tmp-disk`） |
| 判据 | 以该术语为 target 的约束（`con:tmp-disk`［warn］scope=db:primary + 描述） |
| 命中依据 | 打分关键词（tmp / disk / 临时表 / 落盘…） |

**做法**：`OntologyScoring.explain(term_id)` 把术语展开成上述结构（知识留在本体层），
`RCAEngine` 把它并入每个候选/最终根因，并把 `reason` 从
"命中 资源 类关键词: tmp, disk, 临时表" 改写成一句完整结论：

### 11.23 ✅ 已实测：处置动作的判别力（`tools/remediation_efficacy.py`）

第 4 轮的契约只验证**纸面可用性**（动作具体 / urgency 合法 / 声明审批），
无法回答"这条建议在真实故障里**管不管用**"。本轮补上实测闭环：

```
① 基线（无故障）执行全部探针 → 必须阴性
② 注入真实故障 → 等信号成立
③ 真跑一次诊断（确定性）→ 取用户实际会看到的那套动作
④ 再次执行全部探针 → 必须阳性
⑤ 回滚 + 清理
```

**判定必须同时满足"基线阴性 + 故障期阳性"** —— 只测"故障期能报"是不够的：
一个 `> 0` 的判断式在基线不为 0 时永远成立，看起来"有效"其实毫无判别力
（本项目已栽过两次：`slow_queries > 0`、`created_tmp_disk_tables > 0`，见 §11.9）。

#### 结果：动作有效率 10/10（术语级）；探针级 10 有效 / 2 无判别力（后者是刻意设的对照探针）

| 根因术语 | 代表场景 | 探针（基线 → 故障） | 判定 |
|---|---|---|---|
| `rc:conn-exhaust` | db_conn_saturation | Threads_connected 3 → **173** | ✅ |
| `rc:db-cpu-starve` | db_cpu_stress | Threads_running 4 → **19** | ✅ |
| `rc:primary-readonly` | db_primary_readonly | `@@read_only` 0 → **1** | ✅ |
| `rc:replica-lag` | db_replica_lag | SOURCE_DELAY 0 → **60** | ✅ |
| `rc:db-replica-loss` | db_replica_io_stop | 复制线程 `io=ON` → **`io=OFF`** | ✅ |
| `rc:replica-loss` | app_kill_replica | 在册副本 3 → **2** | ✅ |
| `rc:oom-kill` | app_memory_stress | 内存用量/限额 0.11 → **0.94** | ✅ |
| `rc:row-lock` | db_row_lock_hold | 行锁等待速率 0 → **0.229/s** | ✅ |
| `rc:tmp-disk` | db_disk_temp_tables | 磁盘临时表速率 0 → **0.229/s** | ✅ |
| `rc:cpu-throttle` | app_cpu_stress | 节流速率 0 → **0.586/s**（窗口 1m） | ✅ |

> 第一轮实测只拿到 **6/10**，但**其中 3 个是我的探针写错了**，不是动作错：
> `rc:db-replica-loss` 只盯 SQL 线程（而 io_stop 停的是 IO 线程）、
> `rc:replica-lag` 查线程状态（而 SOURCE_DELAY 延迟时两个线程都保持 ON）、
> `rc:oom-kill` 只看 OOMKilled 标志（那是**结果**，内存压力是**过程**）。
> 还有 1 个是我把窗口写成 `[5m]`，把刚注入 1~2 分钟的尖峰稀释到 0.096（阈值 0.1）。
> **教训：探针的阈值与窗口必须与"判定这件事成立与否"的实际口径一致，
> 否则量到的是窗口设置，不是故障。** 修正后 10/10。

#### 实测挖出的 5 个真问题（全部已修）

| # | 问题 | 证据 | 处置 |
|---|---|---|---|
| 1 | **P0 命令引用了不存在的指标** | `rc:cpu-throttle` 写的是 `cc_container_cpu_cfs_throttled_periods_total`，Prometheus 查得 **0 条 series**（正确名 `cc_container_cpu_throttled_seconds_total`）。照着排查只会得到空结果 | 第 5 轮修正 + 契约新增"指标必须存在"（§11.24） |
| 2 | **12 条把散文写进 `command` 字段** | `按 app_instance 对比 P99`、`逐个副本 /health 探活`、`应用日志 / 错误码 1290`… 界面却按等宽命令渲染，既误导也无法自动验证 | 同上，契约新增"command 必须是命令" |
| 3 | **注入器泄漏僵尸：父进程是 `sleep 1800`** | `_db_conn_saturation_inject` 用 `mysql … &` 起 180 个客户端、脚本结尾 `sleep 1800` 挂住 → 父 shell **从不 `wait()`** → 回滚 SIGKILL 掉客户端后它们全变僵尸，**持续最长 30 分钟**（`init: true` 帮不上，因为父进程还活着）。实测累积 **170 个**，把 `doctor` 打红、清理从 17s 拖到 75s | 两处 `sleep` 改成 `wait`（`_mysql_loop` 本来就是对的，属不一致）；杀掉持有者后僵尸归零 |
| 4 | **两张"期望根因"事实表漂移 9/21** | `catalog.ontology_terms` vs `SCENARIO_EXPECTED_TERMS`：6 个场景（`db_replica_lag`/`app_cpu_stress`/`app_network_*`/`app_memory_stress`/`db_replica_io_stop`）在 catalog 里**连根因术语都没有**，3 个漏了合法术语。控制台就是读 catalog 展示"关联本体术语"的 | 对齐 21/21，并把一致性做成 `doctor` 检查项（事实表漂移会让**所有准确率数字都不可信**） |
| 5 | **A/B 口径的准确率被"输入含答案"抬高** | A/B 用例文本是 `fault.title + fault.expected_root_cause`，而后者本身就是**答案的自然语言描述**。换成**真实告警注解**（无泄漏）后：**top1 16/21 = 76%**（本轮 10 个可测场景子集为 9/10），而 A/B 口径是 **20/21 = 95%** | 新增 `--diagnose-only` 回放口径；手册记录两个数字，不再只报 95% |

**关于第 5 条**，5 个 miss 的性质：

* `app_network_delay` → 判成 `rc:cpu-throttle`：该场景声明的告警 `AppReplicaLatencySkew` 的注解自己就写着
  "疑似容器 CPU 节流(cpu quota) 或内存压力" —— **告警文案把人往节流上引**；
* `app_network_loss` → 判成 `rc:replica-hang`：探活失败类告警，"假死"是合理读法；
* `db_primary_readonly` → 判成 `metric:http-error-rate`：该场景只声明了 `AppHighErrorRate`，
  **告警文本里完全没有"只读/写入失败"的信息** —— 属告警覆盖缺口，不是引擎缺陷；
* `db_replica_kill` → 判成 `rc:gateway-down`：**真实的引擎 miss**；
* `res_cluster_memory` → 判成 `rc:oom-kill`：已知的 ground-truth 标注问题（§11.21 第 2 条）。

**结论**：5 个 miss 里 1 个是引擎真错、1 个是标注问题、**3 个是告警文案/覆盖的问题**。
这说明下一步的提升点不在本体，而在**告警质量**（一个告警对应多种根因时，
注解应当给判据而不是给猜测）。

#### 13. 一键流水线 `tools/run_all_verification.py`

#### 已落地的修复：hold 从告警规则的 for 窗口推导

`cluster_rca_verify.py` 的 `--hold` / `--db-hold` 原先硬编码 **55s / 70s**，
而 21 条规则的 `for` 是 **60s×9 + 120s×9 + 180s×3** → 大多数场景在保持期内
**不可能 firing**，端到端退化成了"无输入硬猜"。现已改为：

```
hold = max(告警规则的 for) + 30s      # 本环境 = 180 + 30 = 210s
```

并在启动时打印推导依据；可用 `--hold` 显式覆盖（快速回归时用）。
代价：21 场景的端到端从约 60 分钟增加到约 110 分钟 —— 但这是"真的在测量它声称测量的东西"的代价。

#### hold 修复的子集验证（3 个此前"无告警文本"的场景，`hold=210s`）

| 场景 | hold=70s 时 | **hold=210s 时** | 结论 |
|---|---|---|---|
| `db_conn_saturation` | 覆盖 False、top1 错 | **覆盖 True、top1 = `rc:conn-exhaust` ✅** | 修复**有效**：它的告警只是需要更久才 firing |
| `app_network_delay` | 覆盖 False | 覆盖**仍 False**（新告警是无关的 `MySQLReplicationLag`/`MySQLSlowQueries`） | **告警设计缺口**：声明的 `AppReplicaLatencySkew` 对该故障不触发，等多久都没用 |
| `res_db_memory` | 覆盖 False | 覆盖**仍 False** | 同上 |

所以要把两件事分开：

1. **等待不足**（可修、已修）：告警能 firing，只是 55/70s 不够 → 把 hold 提到 210s 即可；
2. **告警缺口**（另一件事）：该故障**根本不触发它声明的告警** →
   无论等多久都拿不到输入。这一类至少要改监控（补/改规则），不是脚本能修的。

**因此端到端口径应这样读**：把"有告警文本"子集的严格 top1（本轮 **11/14 = 79%**）
作为**诊断能力**指标；全量口径（52%）同时反映**监控可得性** —— 它低于能力值的那部分，
衡量的是"这个环境有多少故障能被告警发现"，本身就是有价值的观测。
**全量 21 场景在 hold=210s 下的复测（约 110 分钟）尚未做**。

#### 第 7 步带出的**最重要**发现：端到端在"告警还没 firing"时就开始诊断

跑这一步时发现 `alert_coverage` 很低、且严格命中率在两次运行间波动很大（17/21 vs 本次更低）。
查下去根因是**等待时间与告警规则不匹配**：

| 项 | 值 |
|---|---|
| 21 条告警规则的 `for` 窗口 | **60s × 9 条 + 120s × 9 条 + 180s × 3 条** |
| 端到端的保持时间 `--hold` / `--db-hold` | **55s / 70s** |

也就是说：`for=60s` 的规则在应用层（55s）**根本来不及 firing**；
`for=120s/180s` 的 12 条规则在两种保持时间下**都不可能 firing**。
于是大多数场景拿不到任何告警文本，端到端实际测的是
**"在没有告警的情况下让智能体硬猜"** —— 这既低估了诊断能力，
也让结果随 LLM 路径的随机性大幅波动（无告警时输入极稀疏，`mode=auto` 会走 agentic）。

**正确做法**：`hold` 必须 ≥ 规则最大 `for` + 一次评估间隔（约 180~210s）。
本轮的完整链路运行用的是**旧默认值**，因此其端到端严格口径数字代表的是
"欠等待"这一口径下的表现，不能当作诊断能力的上界；已在 §11.21 登记并修默认值。

**① `rc:row-lock` 的探针阈值过于贴边**：该探针用
`rate(innodb_row_lock_waits[2m]) > 0.05`，本次实测故障期只有 **0.038**（此前两次是
0.19 / 0.23）→ 判成 `never_on`，动作有效率因此从 10/10 掉到 9/10。
基线是 0，所以阈值放到 0.02 仍能区分 —— **0.05 这个阈值贴着故障量级的下沿，不稳健**。
（这一条属于我自己的探针口径问题，已在 §11.21 登记。）

**② `oom_evidence` 这类"粘性指标"不能作为判别力探针**：`OOMKilled` / `RestartCount`
是**跨场景残留**的（本轮的 `app_oom_kill`、`res_cluster_memory` 会把它置位且不自动清零），
于是基线采集时它就是阳性。**工具按我加的基线污染检测把它单列出来，没有误判成
"always_on = 有效"** —— 这正是那道检测存在的意义。
处置动作有效性因此按"至少一条 P0 探针有判别力"判定，该术语仍记为 effective
（`mem_pressure_ratio` 0.089 → 0.925 是干净的判别证据）。

#### 第 5 步带出的两个新发现

### 11.27 ✅ 告警设计缺口修复（第 1 项）：从"故障发生了但监控看不见"到覆盖

**问题**（§11.21 第 19、2b 项）：21 个故障场景里有 7 个**拿不到任何告警文本** ——
即"故障发生了，但监控看不见"。这不只是测试口径问题：生产上意味着这些故障
不会被发现。另有若干告警的注解**给的是猜测而不是判据**（`AppReplicaLatencySkew`
直接写"疑似 CPU 节流"，而它同时覆盖网络延迟/丢包场景）→ 把诊断引偏。

**取证工具**：新增 `tools/alert_coverage_check.py`（注入 → 等足够久 → 看**声明的告警
是否真的 firing**，不调 LLM、不评分）。它输出三类结论，各自对应一类问题：

| 输出 | 含义 |
|---|---|
| `covered` | 声明告警真的响了 |
| ❌ `declared_but_silent` | 声明了却没响 → **监控缺口** |
| ⚠ `firing_but_undeclared` | 响了却没声明 → **catalog 元数据不准**（测试口径问题） |

#### 找到并修掉的 6 类缺陷

| # | 缺陷 | 证据 | 修复 |
|---|---|---|---|
| 1 | **阈值贴着故障量级**：`MySQLThreadsRunningHigh` 是 `> 20` | 空闲基线 2–4，`db_cpu_stress` 故障期实测**正好 20** → 严格大于永不成立 | 阈值改 `> 12` |
| 2 | **阈值高于故障可达上限 + 窗口稀释**：`MySQLDiskTempTables` 是 `rate(...[5m]) > 0.5` | 同故障下 `[2m]` 实测仅 **0.105**（空闲恒为 0），`[5m]` 再稀释一遍 → 该规则实际从不触发 | 改 `[2m] > 0.05`，`for` 3m→1m |
| 3 | **漏报写法**：`MySQLReplicaDown` 是 `up{job=~"mysql-replica-.*"} == 0` | 容器被删/停后目标从服务发现消失，序列过期 → 该表达式**永远匹配不到** | 改 `count(up{...} == 1) < 2`（序列消失同样减少计数） |
| 4 | **应用层没有 OOM 证据** | 指标清单里只有节流/内存用量，没有任何 OOM/重启计数；OOM Kill 后容器重启、内存回落 → 压力告警消失，"被 OOM 杀过"**完全不可观测** | exporter 新增 `cc_container_oom_kill_total`（cgroup `memory.events` 的只增计数器）+ 新告警 `AppContainerOOMKilled` |
| 5 | **关键故障没有专用告警**：`db_primary_readonly` 只声明泛化的 `AppHighErrorRate`，注解里没有一个字提到"只读/写入失败" | 该场景实测被判成 `rc:slow-sql` | 新增 `MySQLPrimaryReadOnly`（配置态判据 `read_only/super_read_only{db_node="primary"} == 1`） |
| 6 | **注解给猜测而非判据**：`AppReplicaLatencySkew` 的表达式只是"任一副本 P99 > 500ms"（**不是偏斜检查**），注解却断言"其余副本正常 → 单副本资源/节流问题"，并直接猜"疑似 CPU 节流" | 网络延迟/丢包场景也被引向 CPU 节流 | 表达式改为**真偏斜**（`max/min > 2` 且 `max > 0.3`），`for` 3m→2m；注解改为给**判据 + 候选原因 + 各自该看什么指标** |

#### 顺带修掉的两个**注入侧**缺陷（"故障本身不可观测"）

| 场景 | 缺陷 | 修复 |
|---|---|---|
| `res_db_memory` | 压小了 `tmp_table_size` 却**没压 `max_heap_table_size`**；更关键的是 MySQL 8.0 内部临时表默认走 **TempTable 引擎**（受 `temptable_max_ram`/`temptable_use_mmap` 控制），`tmp_table_size` **根本管不到它** → "落盘"症状出不来（实测 `[2m]` 峰值仅 0.028 且 50s 后归零） | 注入期间强制 `internal_tmp_mem_storage_engine=MEMORY`，并同时压 `tmp_table_size` / `max_heap_table_size` / `loops` 200→800（循环跑完就停，覆盖不了保持期）。**修复后 `[2m]` 速率持续 0.10–0.17 整整 200s** |
| `db_disk_temp_tables` | 同样的 TempTable 引擎问题（虽然它能响，但余量很小） | 同样强制 MEMORY 引擎 |

> **这也解开了 §11.21 第 9b 项的谜**：那份"21/21"里有 2 个场景"注入期 0 条声明信号成立"，
> 原因正是这里的**两个问题叠加** —— 信号阈值（0.15 / 0.1）**高于故障可达上限**
> （实测 0.105 / 0.028），加上循环跑完就停。已把两处信号阈值对齐到实测量级
> （0.15→0.05、0.1→0.03），使"注入期信号"这一列真正可用。

### 11.29 ✅ 组件级结论 → 根因级结论（第 3 项）

**问题**：端到端严格口径的未命中里有一类是"答到组件层就停了"——
`app_pause_replica` 给 `app:payment-app-cluster`、`db_replica_kill` 给 `db:mysql-replica`。
它们都是本体里的**合法术语**（所以宽松命中会算对），但不是根因，用户拿不到"到底什么坏了、该怎么办"。

**做法（判据全部来自本体，不另编知识）**：

本体里 `rc:X --attributedTo--> 组件` 这条关系**就是**"根因落在哪个组件上"的显式声明
（ontology_v5 有 15 条），`rc:X --evidencedBy--> metric:M` 说明它的观测佐证（20 条）。
于是当 top1 落在**组件**上时，按两条路径寻找锚定的根因：

1. **候选内锚定**：`role == root_cause` 且 `attributedTo` 指向该组件，且其 `evidencedBy`
   指标出现在**文本显著命中的前 6 个候选**里（证据更强）；
2. **按证据召回**：根因术语自己的关键词没命中、但它的观测佐证命中了 ——
   从证据反推根因（`metric:replica-healthy-count` → `rc:replica-loss` / `rc:replica-hang`）。

找不到锚点就**保持原样**，绝不硬凑；升级时留下 `promoted_from` / `promotion_basis` /
`promotion_evidence`，并在 `reason` 里写明"该结论由组件级候选升级而来"。

**实测（`tools/rootcause_promotion_verify.py`，回放 21 条真实告警文本做 on/off 成对评估）**：

| 口径 | 关闭升级 | 开启升级 | 变化 |
|---|---|---|---|
| 严格命中（根因级） | 17/21 = 81% | **18/21 = 86%** | **+1** |
| 结论落在组件上 | 1 | **0** | −1 |
| top5 命中 | 20 = 95% | **21 = 100%** | +1 |

唯一触发升级的场景 `app_pause_replica`：`app:payment-app-cluster` → **`rc:replica-loss`**（✅ 转正）；
**其余 20 个场景结论完全不变（0 回退）**。

**线上验证**（`POST /api/agent/diagnose`，确定性模式）：

```
root_cause.entity_id = rc:replica-loss      （原来是 app:payment-app-cluster）
role                 = root_cause
promoted_from        = app:payment-app-cluster
promotion_basis      = 本体关系 attributedTo：`rc:replica-loss` 归因到组件 `app:payment-app-cluster`
```

> 为什么用"回放真实告警文本"而不是再跑一遍 2 小时端到端：升级逻辑在**确定性打分**里，
> 而端到端产物已经逐场景记录了当时真正喂给引擎的 `alert_text`。
> 回放这些文本：输入真实（不是含答案的标题口径）、秒级出结果、同一输入下 on/off
> 成对比较，差异只来自升级本身。另加一次线上调用确认端到端可用。

**过程中踩到的坑（值得记）**：第一版把"证据重叠"与**全部 54 个已打分节点**比对，
于是 `rc:cluster-capacity` 靠一个无关佐证指标凑到重叠、再以更高置信度压过真正由证据召回的
`rc:replica-hang`/`rc:replica-loss` —— 升级发生了但升错了。改成只与**文本显著命中的前 6 个**比对后才正确。
（教训：**"在候选里"要问清是"哪个候选集合"**，集合口径不同结论就不同。）

#### A1 · 11c：`db_replica_lag` 的恢复判据改用**配置态**

#### A2 · 5：token 预算变成**硬上限**

**问题**：预算原先只在**循环开头**检查，一次大调用冲过上限、而该次恰好是最终答案时，

依赖的是调参时那几个特定词（"连接池/行锁/只读"），换个说法（"会话/锁住的那几行/不允许写"）
就命中不了 —— 甚至 `ho-05` 掉到了组件级 `db:primary`。

**这组数据本身不改本体**：它是"考卷"不是"教材"。用**同**一组 held-out 去调关键词，
它立刻失去意义（变成第二份训练集）—— 正确做法是：按这些失败模式去补**同义/近义写法**
（另外单独准备一份新的 held-out 作为最终口径），这属于下一轮的工作，本轮只**如实报数**。

#### F · 处置动作的执行闭环（16）

**产物**：`tools/remediation_exec.py`。把本体里的 `remediation` 从"文本建议"变成**可执行且可验证**的动作。

| 动作类型 | 能否自动执行 | 依据 |
|---|---|---|
| **只读取证**（PromQL / SQL 的 SELECT·SHOW·EXPLAIN） | ✅ 自动 | 不改状态 |
| **可逆写操作**（`REVERSIBLE_OPS` 白名单，4 条） | ⚠ 必须 `--approve` | 每条带**逆操作** + **执行后校验**；校验不过则**自动回滚** |
| 散文 / 含 `<占位符>` | ❌ 拒绝执行 | 无法机器执行；拒绝比"猜着跑"安全 |
| 白名单外的写操作 | ❌ 拒绝执行 | 没有声明逆操作 —— 宁可人工 |

**默认 `--dry-run`**；闭环是否算成功不看退出码，而是**根因判据是否真的消失**
（执行前后各跑一次该术语的 P0 探针，复用 `remediation_efficacy.PROBES`）。

**实测（plan + 真执行只读取证）**：

```
处置计划 rc:row-lock → 分类统计 {'promql': 1, 'sql-readonly': 1, 'placeholder': 1, 'empty': 1}
  [0] P0 可执行(只读)  SELECT * FROM information_schema.innodb_trx; ...
  [1] P0 可执行(只读)  rate(mysql_global_status_innodb_row_lock_waits[2m])
  [2] P1 只能人工      KILL <trx_mysql_thread_id>            ← 含占位符，拒绝执行
  [3] P1 只能人工      （空命令）                              ← 拒绝执行
```

**这一跑立刻抓到一个纸面检查发现不了的缺陷**：

```
[0] sql-readonly 执行失败：ERROR 1142 (42000): SELECT command denied to user 'rca_readonly'
```

`rc:row-lock` 的 P0 排查命令查的是 **`sys.innodb_lock_waits`**，而诊断用的只读账号
`rca_readonly` 的授权只有 `PROCESS + REPLICATION CLIENT + creditcard/performance_schema 的 SELECT`
→ **它读不到 `sys` 库**。也就是说：这条"最紧急的排查动作"照着敲只会得到权限错误。
（第 5 轮修的是"指标名不存在"，这次是"库没权限" —— 同一类问题的不同面。）
逐个验证只读账号能读什么之后，已换成本体里的
`performance_schema.data_lock_waits`（MySQL 8 里 `sys.innodb_lock_waits` 的底层来源）：

```
information_schema.innodb_trx       OK
performance_schema.data_locks       OK
performance_schema.data_lock_waits  OK      ← 采用
sys.innodb_lock_waits               DENIED  ← 原命令
```

> 顺带修掉同类"看起来成功"的写法：第一版**没检查执行结果**，
> 上面那条 `Access denied` 发生时界面照样打印"已执行（只读 SQL）"。
> 现在结果一律按真实返回值报告（PromQL 报取值、SQL 报返回字节数、失败报 stderr）。

### 11.35 ✅ 事故：三个页面全 502，而所有容器都 healthy（nginx 缓存上游 IP）

**症状**：控制台的「故障注入」「压测」「成本」三个页面全部报
`502 Bad Gateway`（来自 nginx），但：

```
docker ps                      → rca-agent-backend Up 5 hours (healthy)
curl 127.0.0.1:8088/api/health → 200          ← 直连后端正常
curl 127.0.0.1:3001/api/health → 502          ← 走 nginx 就断
docker logs rca-agent-backend  → 只有来自 172.18.0.1（宿主）的请求，
                                 没有任何来自前端容器的请求
```

最后一行是决定性的：**nginx 根本没把请求发给后端**。

**根因**：`rca-agent/frontend/nginx.conf` 里写的是

```nginx
proxy_pass http://rca-agent-backend:8088;      # 字面主机名
```

nginx 对**字面主机名**只在**启动时**解析一次，并把 IP 缓存到 worker 生命周期结束。
本次会话里我为了应用端口绑定改动重建过后端容器 → 后端换了 IP → 前端那条路**永久断掉**，
直到有人重启前端。

**这类故障最难查的原因**：所有"健康检查"都是绿的 —— 容器 healthy、后端自检 200、
Prometheus 也在正常抓指标，**只有"浏览器 → nginx → 后端"这一跳断了**，
而这一跳恰好是唯一没人监控的。

**修复**（`rca-agent/frontend/nginx.conf`）：

```nginx
resolver 127.0.0.11 valid=10s ipv6=off;              # Docker 内嵌 DNS
set $backend_upstream http://rca-agent-backend:8088;
proxy_pass $backend_upstream;                         # 带变量 → 按 valid 周期重解析
```

**决定性验证**（不是"重启一下就好了"就算过）：
先用占位容器**占住后端原来的 IP**，再重建后端强制它换地址：

```
后端旧 IP = 172.18.0.16 → 占位容器占住 .16 → 重建后端 → 新 IP = 172.18.0.17
前端**未重启**：/api/health 200、/api/chaos/status 200、/api/agent/cost 200  ✅
```

**自动化**：新增 doctor 第 18 项「前端→后端 代理连通（nginx）」——
直接模拟"浏览器 → nginx → 后端"这条真实路径（而不是只看容器状态）。
负向测试：停掉后端 → 该项 **FAIL 且给出准确提示**
（`HTTP 502（502 通常=nginx 缓存了旧的后端 IP，重启前端或改用 resolver 变量）`），总体 FAIL；恢复后 PASS。

> 教训：**"容器健康"不等于"功能可用"**。凡是"经过一次转发/解析/缓存"的链路，
> 都要有一条端到端的探测；只查两端各自的状态，中间那一跳断了谁也看不见。

### 11.36 ✅ 事故：控制台发起 mysql 压测 → 842/842 全失败（目标地址写成了容器的 127.0.0.1）

**症状**：用户从控制台发起一次压测（`20261008T135516Z`，mode=mysql，16 并发 × 30s），结果：

```json
"requests": {"total": 842, "success": 0, "error": 842, "success_rate": 0.0},
"status_codes": {"no-response": 842},
"error_kinds": {"mysql_connect_error": 842},
"latency_ms": {"min": 0.0, "max": 0.0, "p50": 0.0},

**延迟全 0 + 全是连接错误**是关键线索：不是"库被压垮了"，而是**一次都没连上**。

（后端自己连库用的是环境变量 `DB_HOST=mysql`（compose 服务别名），
但这份"事实源"没有传给压测子进程。）

**修复**（两处）：

1. **把连接参数传下去**，并且**沿用后端自己那份环境变量**（不再抄一份默认值）：
   `--mysql-host/--mysql-port/--mysql-user/--mysql-password/--mysql-db`
   ← `DB_HOST/DB_PORT/DB_USER/DB_PASSWORD/DB_NAME`；
2. **压测开跑前先探测目标可达**（`_precheck_stress_target`）：
   MySQL 模式做 TCP 连接、HTTP 模式 `GET /health`，不可达就**当场拒绝并说明原因**，
   而不是把它变成 842 条请求失败 —— 一个配置错误不该长得像一次性能结论。

**验证**（走控制台同一条 API 路径）：

```

修复后： target.mysql = appuser@mysql:3306/creditcard       20/20 成功（0 失败）✅
```

前置探测两个方向都单独验证过：不可达主机/端口 → 拒绝并提示
（`MySQL 目标不可达 ... 容器内跑压测时地址要用 compose 服务名（如 mysql），127.0.0.1 指的是容器自己`）；
可达目标（应用网关 8080）→ 放行。顺带确认了 `mysql` 这个名字**在宿主上解析不了、在容器里能** ——
这正是本次缺陷的本质。

> 影响范围：历史产物里 `mode=mysql/mixed` 只有 2 条 —— 用户这次（全失败）与修复后的验证（0 失败）。
> 也就是说控制台此前所有压测都是 http 模式，**这个缺陷是第一次跑 mysql 模式才暴露的**。
> 用户那次没有造成任何实际负载（请求根本没到 MySQL），可视为一次无效测量，无副作用。

> 教训（与 §11.35 同源）：**"能启动"不等于"打到了目标"**。
> 任何"由 A 拉起 B 去访问 C"的链路，都要在开跑前确认 B 眼里的 C 是同一个 C；
> 容器化的世界里 `127.0.0.1` 的含义随**谁在跑**而变。

### 11.37 ✅ 事故：切页后压测"看起来被中断"（页面状态只活在组件里）

**症状**：在压测页启动压测，切到「智能诊断」页，再切回来 —— 页面一片空闲，
**看起来压测被中断了**。

**先核实"任务到底有没有被中断"**（这一步很重要，否则会去修错的地方）：

```
后端任务 job_323897_stress：status=done  duration=123.1s
产物 stress_20261008T140523Z_mysql.json：total=453  error=0  wall=122.937s
                                          time_series 117 个点（≈完整 120 秒）
```

**结论：任务从头到尾没被打断，是在后端完整跑完的。**（顺带确认 §11.36 的修复也生效了：0 失败。）

**根因**：`App.tsx` 用 `{tab === 'stress' && <StressPage />}` 这种写法切页 ——
**切走就卸载**。任务跑在后端（subprocess）不受影响，但页面一卸载：

- 本地 state 里的 **job id、参数、实时日志、运行中指示全丢**；
- 轮询被 cleanup 清掉；
- 切回来是全新挂载的空页面 → **用户无法区分"任务在跑"和"任务没了"**。

这类"状态只活在组件里"的问题在长任务界面上代价很高：用户不敢离开页面，
也无法确认任务是否还在跑。（故障注入页早已有"接管最近任务 + 每 5 秒认领在跑的任务"的逻辑，
所以只有压测页暴露了这个缺陷。）

**修复**（三层）：

1. **共享状态模块** `src/state/runningJob.ts`：把"当前任务"（**只存 id/类型/标签**）
   放进 localStorage 并广播；任务真实状态始终以**后端**为准，避免本地缓存与后端分叉；
2. **压测页**：启动时先落盘再轮询；**挂载时重新接上** —— 还在跑就恢复轮询与日志
   （`fresh=false`，不清空已有日志，否则看起来像被重启），已结束就显示上次结果；
   任务结束/异常时清除记录；服务端已无此任务（如后端重启）也清除，避免"幽灵任务"；
3. **顶部全局指示**：任何页面都能看到 `⏳ 压测运行中 · http·4并发·25s · 查看`，
   点它直接跳回进度页。

故障注入页也接入了同一共享状态（启动/接管时登记、结束时清除），
它的"认领在跑任务"逻辑本来就存在。

> 长任务界面必须把"哪个任务在跑"这件事持久化到组件之外，

### 11.38 ✅ 执行"慢SQL"建议动作：P0 实测确认，但**索引建议有两处不成立**

对 LLM 给出的三条建议动作逐条执行（P0 只读直接做；P1 属写操作，经用户明确批准后执行）。

**P0（只读排查）—— 确认成立**：`t_txn` **483 万行**，三条语句的 EXPLAIN：

| 语句 | 计划 | 是否如建议所说 |
|---|---|---|
| 慢查询注入 SQL（`COUNT(*) JOIN t_seq WHERE amount>0 AND status<>'VOID'`） | `t_txn` **type=ALL**，rows **4517163**，hash join | ✅ 全表扫描成立 |
| 磁盘临时表 SQL（`GROUP BY customer_id, MD5(...)`） | **type=ALL** + `Using temporary` + **`Using filesort`** | ✅ 成立 |
| DB 内存 SQL（`JOIN t_seq GROUP BY status, MD5(...)`） | `t_txn` **type=ALL** | ✅ 成立 |

**P1a（加索引）—— 建议的列不成立，实测有用的列是另一组**：

1. 建议里的 **`customer_id` 与 `created_at` 早就已经有索引**了
   （`idx_txn_customer(customer_id)`、`idx_txn_created(created_at)`）——
   **LLM 没有查 `SHOW INDEX` 就断言"缺少索引"**，这部分建议是空转；
2. 真正有用的是 **`(status, amount)`**（建议里没提）：
   ```sql
   ALTER TABLE t_txn ADD INDEX idx_txn_status_amount (status, amount),
         ALGORITHM=INPLACE, LOCK=NONE;      -- 在线 DDL，不阻塞读写
   ```
   复测 EXPLAIN：慢查询 SQL 的 `t_txn` 由 **type=ALL / rows 4517163**
   → **type=range / idx_txn_status_amount / `Using index`（覆盖索引）**；DB 内存 SQL 也由全表扫变为索引扫描。
3. 我一度还按建议加了 `idx_txn_customer_id(customer_id)`，实测发现它与既有
   `idx_txn_customer` **完全同列** → 纯属重复索引（白占空间、拖慢写入），**已 DROP**。
   最终索引：`idx_txn_customer(customer_id)`、`idx_txn_created(created_at)`、
   `idx_txn_status_amount(status, amount)`。
   回滚语句：`ALTER TABLE t_txn DROP INDEX idx_txn_status_amount;`
4. **任何索引都修不了那两条 `MD5(...)` 语句的 `Using filesort`** ——
   MD5 是逐行计算，无法用索引做分组；它们本来就是**注入器制造的故障本身**。

**P1b（把应用层聚合下推并加 LIMIT）—— 前提不成立，未执行**：
那两条"业务 SQL"（`GROUP BY customer_id + MD5(...)`）**只存在于 `tools/chaos/catalog.py`**，
是**故障注入 SQL**，不是应用代码；应用（`demo/app/server.js`）的读路径
（`SELECT ... ORDER BY txn_id DESC LIMIT ?`）**本来就有 LIMIT**，也没有 JS 侧遍历大表做聚合。
照这条建议去改，等于去改注入器 —— 而那正是它**故意**要慢的地方。

**真实存在的等价问题**（建议里没提到，但值得修）：应用的副本探针每 20 秒执行一次
`SELECT COUNT(*) FROM t_txn`（483 万行，仅用于展示 `txnRows`），3 个副本各跑一遍 ——
这才是应用侧真正可以避免的大表全扫。建议改为缓存该计数（如 60s TTL）或直接用
`information_schema.TABLES.TABLE_ROWS` 近似值。

> 教训：Agent 的处置建议里有两条**未经核实的前提**（"缺 customer_id/created_at 索引"、
> "应用层在遍历大表做聚合"）。这类错误用 P0 一步就能证伪 ——
> **先 EXPLAIN / 先 SHOW INDEX，再决定建什么索引**，顺序反了就会白建索引、甚至改错组件。

### 11.39 ✅ `txnRows` 加 60s 缓存：应用侧最贵的重复查询被削掉 4 倍

**背景**：应用副本探针（每 20s 一次）的 SQL 里带 `(SELECT COUNT(*) FROM t_txn)`，
只为在拓扑/指标里展示"表里有多少行"。`t_txn` 有 **483 万行**，这个 `COUNT(*)` 是全索引扫描，
而它每 20s × 每个副本 × 每个应用实例都要跑一遍。

**改法**（`demo/app/server.js`）：60s TTL 缓存 + **缓存新鲜时探针 SQL 里不再带子查询**：

```js
const TXN_ROWS_TTL_MS = Number(process.env.TXN_ROWS_TTL_MS || 60000);
// 缓存新鲜 → 用 `NULL AS txnRows` 占位；取回后用缓存值**覆盖**，消费方看到的仍是数字
```

不是"少查几次"，而是**把子查询从探针语句里摘掉**（缓存命中时那条 SQL 根本不碰 `t_txn`）。
需要更实时可设 `TXN_ROWS_TTL_MS=0` 关闭缓存。

**验证**（`performance_schema.events_statements_summary_by_digest` 实测，不是推算）：

| 口径 | 改动前 | 改动后 |
|---|---|---|
| 两个副本上该语句的合计执行速率（60s 窗口） | **20 次/分钟** | **5 次/分钟** |

语义未变：`/topology` 连续三次都返回 `txnRows = 4833992`（是数字，不是 null），
只是最多滞后 60s。应用三副本重建后 `healthy`，`doctor` 总体 PASS。

> 注意基线口径：探针打的是**副本**，所以要在副本上量 ——
> 我第一次量的是主库，只看到 1 次/分钟（摘要表是**每个 MySQL 实例各自**的），
> 差点据此得出"这个查询本来就不频繁、不必优化"的错误结论。

### 11.40 ✅ 慢查询门槛从 0.1s 调到 1s + 加 `min_examined_row_limit`

**判断依据（先量再改）**：原门槛 `--long-query-time=0.1` 的问题不是"严格"，而是**买不到东西却赔掉信号质量**：

| 观测 | 0.1s 门槛下 | 说明 |
|---|---|---|
| 空闲时 `Slow_queries` | **1.4 次/分钟且在涨** | 没有任何故障 |
| 被记为慢查询的语句 | `SELECT COUNT(*) FROM t_txn`（0.58–2.9s，纯展示用）、`INSERT INTO t_txn`（均 **396ms**，5 万次） | 正常写入路径 |
| 注入类慢语句实测均值 | **2.2s / 16.6s / 52.6s / 170s** | 比 1s 门槛高 **20–1700 倍** |

后果落在诊断侧：`mysql_global_status_slow_queries` 是本体里 `rc:slow-sql` 的观测证据，
门槛过严会让它随正常流量上涨 → 该术语被**误证**（"环境本来就慢"被当成"有慢 SQL"）。

**改法**（`rca-agent/docker-compose.yml` 三处 / `demo/docker-compose.yml`）：

```yaml
- --long-query-time=1              # 与生产常用口径一致
- --min-examined-row-limit=10000   # 只记"又慢又扫了很多行"的
```

单靠时间阈值永远在"太吵"和"漏报"之间二选一；配上行数门槛，挡掉展示类 `COUNT(*)`，
同时**保留注入故障**（它们要扫 400 万行）。同步更新了 `catalog.py` 注入报告里的描述字段
（`slow_query_logging`），`tools/check_metrics.py` 只查 `slow_query_log` 是否为 ON，不受影响。

**验证（全部实测）**：

| 项 | 结果 |
|---|---|
| 三个节点新设置生效 | `long_query_time=1.000000`、`min_examined_row_limit=10000` ✅ |
| **空闲 90 秒慢查询增量** | **0 / 0 / 0 次**（改前主库 1.4 次/分钟）✅ |
| 重启后摘要表 | 无任何累计耗时 >100ms 的语句 ✅ |
| 重建后复制健康 | `mysql_up` = primary/replica-1/replica-2 全 **1**；延迟 **0/0**；applier/connection 均 **ON** ✅ |
| **故障仍可检出** | 注入 `db_slow_query_flood` → **`MySQLSlowQueries` 在 ~140s 触发**，主库 `Slow_queries` 累计升到 **127** ✅ |

> 一处**待复验**（如实记录）：注入时那次工具内的信号等待窗口（120s）报 `signal_observed=false`，
> 而告警在 ~140s 才响 —— 说明**信号起点比 0.1s 门槛时略晚**（查询要先跑完、超过 1s 才进慢日志）。
> 因此 `fault_verify` 对该场景用的 `--signal-timeout 50` 可能偏紧，需要在下一轮全量验证里复核
> （这是"改完必须回归"的典型项，不能靠推断放过）。

**这一步暴露了一个更值得记的问题（判据窗口 > 验证等待）**：

调高阈值后复跑该场景注入验证，结果是 **1/1 通过，但"注入期全部声明信号成立 0/1、完全未观测到信号 1/1"**：

```
signals: max(rate(mysql_global_status_slow_queries{db_node="primary"}[2m])) > 0.45
verify 只等 ~75s（--signal-timeout 50 + 裕量）→ 2 分钟窗口根本没铺满 → 结构上不可能成立
```

**为什么以前能过**：`long_query_time=0.1` 时，应用自身的 `INSERT`（均 396ms）**一直**在被记成慢查询，
这个计数器**注入前就在涨** → 2 分钟窗口里本就有历史 → 注入后很快满足判据。
也就是说：**它一直是因为"环境噪声"才通过，判据本身是坏的** —— 把噪声去掉才暴露出来。

**修法**（改判据，不动阈值）：窗口 `[2m]` → `[30s]`（阈值与语义不变，>0.45/s ≈ 27 次/分钟）：

| | 修复前 | 修复后 |
|---|---|---|
| `signal_observed` | false | **true** |
| 注入期全部声明信号成立 | **0/1** | **1/1** |
| 完全未观测到信号 | 1/1 | **0/1** |
| 场景结果 / 耗时 | 1/1 通过 / 227.2s | 1/1 通过 / **148.3s** |

**顺带扫了同类隐患**（全部场景里窗口 ≥2m 的判据共 8 条，分布在 6 个场景）。
要分清两类：
- **`> 0` 类**（`db_primary_readonly` 的 `rate(503[2m]) > 0`、`app_oom_kill` 的 `increase(...[5m]) > 0`）：
  只要计数器一动就成立，**不受窗口铺满影响**，安全；
- **带幅度阈值的 2m 窗口**（`db_row_lock_hold > 0.02`、`db_disk_temp_tables > 0.05`、`res_db_memory` 同类）：
  **属于同一隐患**。它们在真实流水线里能过，是因为这些场景有**多条**信号、别的信号先成立；
  单看那一条判据，75s 内同样可能无法成立。建议下一轮统一按"**窗口必须短于验证等待**"逐条复核。

> 规则：判据的**时间窗口必须短于验证等待**，否则它不是"严格"，而是**永远红不了**。
> 与"永真检查"一样，这种判据不会告诉你任何信息，只会让人误判故障没造成。

**顺带修掉一个既有缺陷（与本轮阈值无关，但被 `doctor` 抓出来）**：

`doctor` 报 `容器无僵尸进程 FAIL rca-agent-backend=3(curl=3)`。查实链条：

```
后端容器 PID 1 = python3 -m uvicorn ...   ← 不是 init
PID 64407  PPID 1  Z  [curl]              ← 被 PID 1 收养且永不回收
```

后端 Dockerfile 的 `HEALTHCHECK ... CMD curl -fsS /api/health` 每 30s fork 一次；
而后端容器**没有 `init: true`** → PID 1 是 uvicorn，**不会 `wait()` 被收养的孤儿** → 僵尸只增不减。
（`cc-app-gateway` / `rca-agent-frontend` 同样缺；MySQL 与应用副本本来就有。）

**修法**：给 `rca-agent-backend`、`rca-agent-frontend` 补 `init: true`（PID 1 变 tini）并重建。

| 项 | 修复前 | 修复后 |
|---|---|---|
| `HostConfig.Init` | false | **true** ✅ |
| `容器无僵尸进程` | FAIL（3 个 `[curl]`） | **OK** ✅ |
| `前端→后端 代理连通` | OK | **OK**（§11.35 的 resolver 修复经受住了重建）✅ |
| `doctor` 总体 | FAIL | **PASS** ✅ |

> 踩坑记录：第一次重建时我把服务名写成 `cc-app-gateway`（那是 `container_name`，
> **服务名其实是 `app-gateway`**），`docker compose up` 遇到未知服务名**整体报错、什么都没重建**，
> 于是僵尸数没变、看起来像"加了 init 也没用"。**重建类操作必须核对 `docker compose config --services`
> 给出的真实服务名**，不能拿 `docker ps` 里的容器名去凑。
> 遗留：`app-gateway`（nginx）仍未加 `init: true` —— nginx master 自己会收子进程，暂未暴露问题，
> 但为与既有约定一致，建议下一次一并补上。

### 11.41 ✅ 判据可观测性专项：4 个"永远红不了"的场景 + 一个结构性观测缺口

**起点**：全量回归里"注入期信号全部成立"只有 **16/21**（4 个场景完全未观测到）。逐个查下去，
发现它们不是"故障没造成"，而是**判据本身不可能成立** —— 与 §11.40 修的"窗口长于等待"同源，
但这一轮四种成因各不相同，值得单独成节。

**终点**：**21/21 场景通过、注入期信号成立 20/21、完全未观测 0/21**。

#### 成因一：容器内计数器被重启清零（结构性缺口 → 新增容器外导出器）

`app_oom_kill` 的判据含 `increase(cc_container_oom_kill_total[5m]) > 0`。实测：

```
注入层确认：        "oom_observed": true   "limit_applied": true
同时刻容器内计数器： …a4a4=0  …9efb=0  …404a=0        ← 三个实例全为 0
```

原因：该计数器是**容器内**读 cgroup 得到的；容器被 OOM 杀掉并重启后**新容器从 0 开始**，
Prometheus 眼里这条序列"生来是 0" → `increase()` 永远为 0。（早先那次"覆盖成功"，是内核杀的
是容器里的 `stress-ng` **进程**、容器没重启，计数器留在原地才看得见。）

**修法**：新增 `rca-agent/monitoring/container/exporter.py` —— **容器外**读 Docker API，
暴露 `cc_container_restart_count` / `cc_container_oom_killed` / `cc_container_running`。
只用标准库走 UNIX socket，因此镜像用干净的 `python:3.11-alpine`，**不需要 Dockerfile、不需要 docker CLI**。
告警规则改为 `increase(cc_container_oom_kill_total[5m]) > 0` **or** `increase(cc_container_restart_count[5m]) > 0`，
场景判据同样换成容器外证据。实测新指标立即出现且**不随重启消失**：

```
container=rca-agent-payment-app-1 restart_count=1
container=rca-agent-payment-app-2 restart_count=1
container=rca-agent-payment-app-3 restart_count=0
```

> 一般化：**"X 发生过"这类证据不能放在 X 自己身上**。凡是被观测对象可能整体重启/消失的量，
> 都必须由**外部**观测者持有。

#### 成因二：证据出现时机 ≠ 判据窗口（`db_replica_kill`）

原判据想抓 `mysql_up=0` 的瞬态，实测时间线：

```
08:40:57 杀掉副本容器  →  08:43:44 副本才回来（冷启动 167 秒）
等待预算 120s < 167s  →  窗口在副本回来之前就到期
且容器在跑时 Prometheus 仍返回**陈旧的高 uptime**（1416s）→ 只看 uptime 必然为假
```

**修法**：判据取**并集** —— `count(mysql_up{db_role="replica"} == 1) < 2` **or** `min(uptime{db_role="replica"}) < 180`。
前者在宕机期间约 15s 即可观测并持续全程，后者覆盖"重启已发生"这一持久证据。**单验 83.7s 通过**。

#### 成因三：阈值物理上达不到（`db_slow_query_flood` / `db_row_lock_hold`）

- 慢查询：`rate(...[30s]) > 0.45`（≈27 次/分钟）—— 单条注入 SQL 约 2.2s，受并行度限制，
  30s 窗口内只累计到个位数 → **降到 0.15**（空闲基线为 0，裕量充分）。
- 行锁：窗口 `[30s]` 太窄 + 等待 50s 太短 → 窗口改 `[1m]`，等待预算提到 **120s**。

#### 成因四：**恢复判据的语义被我写反了**（`app_oom_kill`）

`recovered_signals` 的语义是"**要消失的症状**"（必须变为**假**才算恢复），
不是"恢复后应成立的条件"。我写成 `count(up{job="payment-app"} == 1) >= 3`（健康时为真）
→ 永远等不到它为假。实测证据极其直白：

```
recovery_checks: ok=False waited=150.0s
  expr = count(up{job="payment-app"} == 1) >= 3
  result = ['3']            ← 条件明明已满足，检查却判失败
```

**修法**：改成 `< 3`（"副本没齐"才是要消失的症状）。**单验 74.4s 通过**。

#### 一个工具链事故：PowerShell 的 UTF-8 BOM 打崩 Prometheus

用 `Set-Content -Encoding UTF8` 改 `alerts.yml` → **写入 UTF-8 BOM**（首 3 字节 239,187,191）
且 YAML 结构被破坏 → Prometheus 规则加载失败、**崩溃循环 10 次**（`yaml: line 24: did not find expected ...`）。

恢复过程有两点可复用：
1. **改动发生在 `git add` 之后 → 索引里是干净版本**，`git checkout -- <file>` 一步还原；
2. 改写用 `[IO.File]::WriteAllText($p, $t, (New-Object Text.UTF8Encoding($false)))`（无 BOM），
   并**回读首 3 字节**确认（35,32,61 ✓）。

> 规则：**改配置后必须回读校验** —— YAML 看首字节 + `docker compose config` +（Python）`py_compile`。
> "命令执行成功"不等于"文件是对的"。

1. **证据不能放在被观测对象自己身上**：会被重启/销毁的量，必须由外部观测者持有。

### 11.42 ✅ 「19/20 → 20/20」差的最后 1 分：不是知识缺口，是**输入撞车**

**起因**：第 6 轮把 `con:oom-detection` 的"内存压力/内存不足"删掉、发布 `ontology_v6`，
闸门 9/9 通过 —— 但端到端严格口径仍是 **19/20**，`res_cluster_memory` 还是判 `rc:oom-kill`。
当时的解释是"本体标注歧义、两个答案都说得通"。**这个解释是错的。**

**实测（成对，回放端到端当时真正喂给引擎的 `alert_text`）**：

| 口径 | 结果 | 证据 |
|---|---|---|
| 第 6 轮闸门（`memory_semantics`，9 条不变量） | 0/9 → 9/9（Δ+1.000，accept） | `.evoontology/evolution/run_8/run.json` |
| **引擎严格命中**（同一批真实输入，v5 → v6） | **19/20 → 19/20（Δ0，0 个 case 变化）** | [`reports/oom_evidence_replay.json`](../reports/oom_evidence_replay.json) |
| 继续收紧到"只剩已被杀的硬证据" | 19/20（**无变化**） | [`reports/oom_counterfactual.json`](../reports/oom_counterfactual.json) |
| 再加 `rc:oom-kill` 的 `negative_keywords` | 19/20（**无变化**） | 同上 |
| 硬推 `rc:cluster-capacity` | **18/20**（转正 1、回退 2：`app_memory_stress` + `app_oom_kill`） | 同上 |
| 单场景端到端复测（v6 激活，真注入） | 仍 `rc:oom-kill`，严格未命中 | [`reports/rca_retest_res_cluster_memory.json`](../reports/rca_retest_res_cluster_memory.json) |

**根因一：词改在了错的那一层。** 关键词有两份 —— v6 只清了 `con:oom-detection`（*Constraint*），
而 `rc:oom-kill` 的 *Term* 词典（id/name + `scoring_keywords`）本来就含 `oom`/`kill`/`被内核杀死`；
`con:oom-detection` 在 V1/V2 下**已经完全不再命中**，结论却纹丝不动。而且文本贴合度是
`min(weighted, 3)/3`（**会饱和**），命中数早就超过 3 的术语加负向词也压不下去 —— 这就是
"闸门绿了、结论没动"的机制。

**根因二（真正的原因）：两个语义不同的故障拿到了逐字节相同的输入。**

| 场景 | 注入 | 期望根因 | 当时声明的告警 |
|---|---|---|---|
| `app_memory_stress` | `selector=roundrobin`：**单副本** 200MB | `{metric:mem-pressure, rc:oom-kill}` | `AppContainerMemoryPressure` |
| `res_cluster_memory` | `selector=app-all`：**3 副本各** 220MB | `{rc:cluster-capacity, metric:mem-pressure}` | `AppContainerMemoryPressure` |

两者拿到的 `rca_hint` 都是
`payment-app 容器内存使用逼近 cgroup 上限，存在 OOM Kill 风险，容器可能被内核杀死并重启`。
确定性引擎对同一段文本只能给**同一个** top1，而两个 case 的期望**互斥** ⇒ **这一对至多命中一个
⇒ 严格上限被钉死在 19/20**。这不是"标注歧义"，是**基准的输入设计缺陷**：
集群级故障（全部副本同时越限）被喂了逐容器视角的告警。

**修法（不动 ground truth、不动本体知识）**：缺的是**集群级告警**。新增

```yaml
- alert: AppClusterMemoryCapacity            # rca-agent/monitoring/prometheus/alerts.yml
  expr: count(cc_container_memory_working_set_bytes
              / (cc_container_memory_limit_bytes > 0) > 0.85) >= 3
  for: 1m
  labels: {severity: P1, layer: resource, onto_constraint: con:cluster-capacity}
  annotations:
    rca_hint: "payment-app 应用集群全部副本同时内存越限（3/3 副本 working set 逼近 cgroup 上限），集群整体内存容量不足，需扩容或提高配额"
```

并让 `res_cluster_memory` 声明它（`alert_names=["AppClusterMemoryCapacity"]`）。
判据用**同时越限的副本数**：单副本压力永远不满足 `>= 3`，所以这不是"换个说法把答案喂进去"。

**验证（真注入 + 真告警 + 真引擎）**：

| 场景 | 新告警是否触发 | 根因 | 严格 |
|---|---|---|---|
| `res_cluster_memory` | ✅ `AppClusterMemoryCapacity` | `rc:cluster-capacity` | ✅ |
| `app_memory_stress`（对照） | ❌ **未触发**（count=1） | `rc:oom-kill` | ✅ |

成对分数（**同一本体 v6、同一份 ground truth**，只换 `res_cluster_memory` 的输入）：
先导验证只重跑了受影响的两个场景，随后做了**全量 21 场景重跑**，两者结论一致：

| 口径 | 改前 | 改后 | 变化 |
|---|---|---|---|
| 严格命中（根因级）· 先导（2 场景重跑 + 成对回放） | 19/20 | **20/20** | **+1** |
| 严格命中（根因级）· **全量 21 场景真机重跑** | 19/20 | **20/20** | **+1** |
| top5 命中 | 20/20 | 20/20 | +0 |
| 逐 case 变化 | — | **恰好 1 个**（`res_cluster_memory`） | — |
| 回退 | — | **0** | — |
| `AppClusterMemoryCapacity` 触发范围 | — | **仅 `res_cluster_memory`**（对照场景未触发） | — |

全量重跑的其余口径：注入 21/21、恢复 21/21、告警覆盖 20/21（`db_conn_saturation` 仍未覆盖，
两轮一致，属既有问题、与本轮改动无关），平均耗时 14.5s/例、0 token。

证据：[`reports/rca_diagnosis_report_postfix.json`](../reports/rca_diagnosis_report_postfix.json)（真机全量）、
[`reports/e2e_postfix_ab.json`](../reports/e2e_postfix_ab.json)（两轮全量成对 A/B）、
[`reports/oom_input_fix_ab.json`](../reports/oom_input_fix_ab.json)（先导）、
[`reports/rca_retest_oom_input_fix.json`](../reports/rca_retest_oom_input_fix.json)（两场景真机复测）；
改前基线保留在 [`reports/rca_diagnosis_report.json`](../reports/rca_diagnosis_report.json)。
工具：`tools/ontology_ab_replay.py`（本体 A/B 与**输入 A/B** 两种模式）、
`tools/oom_evidence_counterfactual.py`（关键词反事实）。

**沉淀成 4 条**：

1. **"闸门通过" ≠ "结论变对"**：本轮闸门口径测的是"本体自己是否自洽"，不是"引擎会不会改判"。
   改语义的轮次必须附一个**引擎层**的成对观察量（本轮第 6 轮其实记了 `0.952 → 0.952`，但没人看）。
2. **报"本体说不清"之前，先确认输入是否足以区分**：两个语义不同的故障拿同一条告警文本，
   本体怎么改都无解。**先看输入，再看知识。**
3. **严格口径的上限是可以证明的**：找到一对"同输入、异期望"的 case，上限即定
   （本例 = `20 - 1 = 19`）。这比"再调一版试试"便宜得多。
4. **改输入不是作弊，但必须证明它真的在区分故障**：新判据要在**对照场景上不触发**
   （此处单副本场景未触发），否则就只是把答案写进了输入。
