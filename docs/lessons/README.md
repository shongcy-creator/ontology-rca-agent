# Lessons from building this project

这个目录记的是**真实发生过的事故**，不是"最佳实践清单"。每篇的结构固定：
**症状（可测量的）→ 为什么难查 → 根因（带证据）→ 修法 → 可迁移的规则**。

它们的共同点是同一个模式：**一切看起来都正常，但功能是坏的**。
在运维智能体这个领域，"看起来正常"是最贵的失败模式 ——
它同时骗过人和骗过监控，而**被注入的智能体自己也可能被它骗**。

## 用法

这些不是"别人的坑"，而是**这个仓库自己的坑**，都带着 commit 与实测数字。
如果你在做故障注入 / 可观测性 / 自动化诊断，建议重点看 **05** 与 **06** ——
它们不是操作失误，而是**设计缺陷**，而且都会让你的验证结论静默失真。
